# Wisp 0.6.0 — design spec

Status: DRAFT 2026-11-21, awaiting the user's answers to the open questions at the end. The theme and the features below were agreed with the user on 2026-11-21 and are binding; the open questions are not. Inputs: the 0.5.0 spec (`docs/plan/specs/2026-11-19-wisp-0-5-0.md`), the roadmap (`docs/plan/roadmap.md`), the landing-site mock (`~/workspace/wisp-site/index.html:19`, tokens at `~/workspace/wisp-site/styles.css:1`) and the private design canvas https://claude.ai/artifact/GRWzJYzqdFoXYSTcw2Tg8n (boards: 1 Main window, 2 Variables view, 3 URL bar states, 4 Buttons, toolbar and menus). Citations are `path:line` at `8133861` (0.5.0 released). Guesses are marked GUESS.

## Outcome

Wisp 0.6.0 is a lean-up and polish release. Nothing specific is broken; the aim is an app a first-time user finds intuitive. The window takes the look of the landing-site mock, with a spacing and radius scale. JSON bodies show one line per row with line numbers, long values wrap, and the page never scrolls sideways. JSON, and if there is room XML and HTML, are colour-highlighted. The URL bar shows the resolved URL that Send will use, and each `{{token}}` explains itself on hover or focus. One Variables view replaces the secrets panel and the per-request Vars tab, and for the first time edits environment variables and collection and folder defaults in the app. A full menu bar and a first-run empty state give every command a visible home.

**Success:**
- A first-time user can find and edit any variable or secret without reading docs (hand test, scripted in the 198-style checklist).
- Every palette command is reachable from a menu, and the palette still finds all of them.
- Request and response JSON bodies render one line per row, wrap long values inside the panel, and never scroll sideways.
- The resolved URL is visible before Send, secrets masked.
- Both themes pass the contrast tests, extended to the new tokens.

## User decisions (binding, 2026-11-21)

- **Theme:** "lean-up and polish".
- **Size is a goal, not a gate.** This relaxes 0.5.0's D-1 (a 16,000,000 B hard gate, 15,900,000 B soft line). Windows GUI and CLI sizes are measured and reported per wave and in the release notes. A jump of more than about 250 KB in one task needs a line of justification in its HISTORY entry. There is no hard stop.
- **Variables model:** Bruno's model was rejected as too complicated, and its global → folder → request → root-secrets chain as unintuitive. The Variables view below is the replacement.
- **Out of scope:** a plugin system, new auth types, text diff in compare, scripting.
- **Later idea, recorded, not scheduled:** plugins as request-lifecycle hooks, or an outcome-driven request sequence (for example a token request that feeds an authorised call, capturing values from one response into the next). It must be reconciled with 0.5.0's D-K, which dropped general scripting.

## Goals and non-goals

**Goals:** the visual language and tokens; body rendering; syntax highlighting behind a small interface; the resolved-URL preview and token cards; the Variables view; the menu bar and button system; the first-run empty state; the landing-site refresh.

**Non-goals (later, with reasons):**

| Later | Why not 0.6.0 |
|---|---|
| Plugin system, request hooks, request sequences | Agreed out of scope; needs a design reconciled with D-K. Only the highlighter interface is kept plugin-shaped. |
| New auth types, text diff, scripting | Agreed out of scope. |
| `wisp-cli compare` and diff export | Still needs export redaction (0.5.0 spec, non-goals table). Not part of a polish release. |
| File-format change | None intended; see "No file-format change". |

## Shape

Almost everything is `crates/app`, the only crate that touches GPUI. Exceptions:

- **Variable listing for the Variables view:** `wisp-core` already has `lookup_all` (`crates/core/src/resolve/engine.rs:82`), which returns every scope's value for a name, and `lookup_var` (`:155`). Both are `pub(super)` or specific to one name; the view needs a public "names used by this request, each with its winning value and the shadowed ones" function. This is the one core addition, pure and without GPUI.
- **Defaults editing:** `save_collection_defaults` (`crates/storage/src/collection.rs:194`) and `save_folder_defaults` (`:415`) exist and have no app caller. No storage change is expected.
- **Tokens:** colours live in `crates/app/src/theme.json`, light and dark. The spacing and radius scale is new; today spacing and radii are inline gpui styles.

## Feature 1 — Visual language

Move the app to the look of the landing-site mock: dark background `#1b1d24`, panel `#16181e`, raised `#23262f`, text `#e4e6ee`, muted `#9ba1b2`, border `#323644`, accent `#aab6ff`, with the light variant under `html[data-theme=light]` (`~/workspace/wisp-site/styles.css:1`). Then go further with UI/UX practice: consistent spacing, hit targets, focus rings, and states for hover, active, disabled and selected.

The design canvas boards fix these elements:

- **Top bar:** collection switcher and environment switcher as visible buttons; Variables, History and Import buttons; a search field that opens the palette (⌘K); a settings icon.
- **Sidebar:** the method colour on every request (GET green, POST gold, PUT purple, DELETE red); new-request and new-folder icon buttons; the selected row with an accent tint.
- **Tabs:** a dot for unsaved changes.
- **Request bar:** method picker; URL field with token chips; Save with its shortcut; a primary Send with its shortcut. Under it, the resolved URL line, a copy button, and chips for the auth source and problems.
- **Request sub-tabs:** Params, Headers, Body, Auth, Variables, Checks, Notes, each with a count.
- **Response header:** status pill, time, size, checks result; a segmented Body / Headers / Compare / Explain; copy and save-to-file icon buttons.
- **Status bar:** environment, trust state, history state, saved time, version.
- **Tokens:** colours in `theme.json` (both themes), plus a spacing scale and a radius scale as named constants in one module. Inline magic numbers in touched files move onto the scale.

Fonts are an open question (Q2).

## Feature 2 — Body rendering

User requirement. Request and response JSON bodies show one JSON line per row, with line numbers. Long values wrap inside the panel. The page never scrolls sideways. Today `crates/app/src/pretty.rs` pretty-prints JSON without colour and the request body uses gpui-component's `EditorState` (`=0.8.1`, `default-features = false`, `Cargo.toml:53`); whether the editor can soft-wrap with a line-number gutter is a question for the architect spike (Q1). Non-JSON bodies wrap too.

## Feature 3 — Syntax highlighting

The app has none for bodies. `crates/app/src/highlight.rs` colours only `{{var}}`. 0.6.0 adds token colouring for JSON (must), and XML and HTML (should), in the response view and the request body editor. Colours come from `theme.json` under `highlight.syntax`, light and dark.

The tokenizer sits behind a small internal interface (a language gives a function from text to a list of token spans, each with a kind). A later plugin could provide a language through it. No plugin system, loader or public API ships in 0.6.0. Large bodies must not stall the UI: highlight is bounded by the same display cap the response view already applies, and past it the body shows uncoloured. The engine choice is Q1.

## Feature 4 — Resolved URL preview and token cards

Under the URL field, a line shows exactly what Send will use, with the filled-in parts brighter and a copy button. Secrets stay masked in the preview and in copies. A "Copy with secrets" path reveals before copying and says so.

- **Token card** on hover or focus: the value, its source scope, "also set in … (overridden)", Edit value, and Open in Variables. It is reachable by keyboard.
- **A token with no value:** a red wavy underline, a message, and "Set value" in place. Send asks first.

The URL bar already resolves for the context strip (`crates/app/src/ui/url_bar.rs:373-422`; `strip_text` at `:84`, `preview_problems` at `:144`) through `resolve_with` (`crates/core/src/resolve/engine.rs:280`) and `lookup_var` (`:155`). The preview reuses that path; it adds no second resolver. A test asserts the preview text equals the URL of the prepared request.

## Feature 5 — One Variables view

The view replaces the separate secrets panel (`crates/app/src/ui/env_secrets.rs`) and absorbs the per-request Vars tab (`crates/app/src/ui/request/vars.rs`) as its "this request" scope. Today environment plain variables and collection and folder defaults have no in-app editor; they are edited as files.

**Precedence, as the code has it** (`crates/core/src/resolve/engine.rs:46-80`): request, then folders (innermost first), then environment secrets, then environment variables, then collection defaults. **This differs from the order written in the agreed brief** ("request › folder › collection › environment"): the collection is the lowest scope, below the environment. The one-line rule in the UI states the real order: "the closest value wins: request › folder › environment › collection". Secrets win over plain variables of the same name in an environment. If the user wants the brief's order instead, that is a behaviour change to the resolver and needs its own decision; this spec does not make it.

**Behaviour:**

- The view opens on "variables this request uses": one row per name, the value that will be sent, and a source chip (request, folder, collection, environment) in a distinct colour. Secrets show masked with a lock and their store (Keychain or file).
- Expanding a row shows where else the name is set, with overridden values struck through, and where it is used.
- Missing names are red rows with "Set". Names set but unused go in a collapsed "not used by this request" section. A toggle shows everything in the environment.
- The edit panel has: the value; a Secret checkbox ("hidden on screen, never written to collection files or history"); and "Change it for: every request in <env> / only this request", with "more places: folder, collection" as a secondary option.
- Secret storage becomes one setting per environment: "Secrets in homelab are kept in: macOS Keychain ▾". Switching moves them all in one step, using the existing move logic (`EnvAction`, `crates/app/src/vault.rs:642`). Environments that mix stores are Q3.
- Saving is explicit, as elsewhere. Changed rows show "unsaved".

**Placement** is Q5. The Variables sub-tab of the request, the top-bar button and the palette command all open this view.

### No file-format change

No file-format change is intended. `format = 1` is unchanged: the view reads and writes the same `[[vars]]`, environment and defaults files through the existing storage functions. A change would be triggered only by one of: a new variable attribute persisted in the file (for example a per-variable description), a per-environment secret-store field written into a collection file (the setting is meant to live in per-user state or the existing binding registry, not in the collection), or a different precedence order. Any of these stops the task and returns to the user.

## Feature 6 — Buttons and menus

Today 18 of the 24 palette commands (`crates/app/src/palette.rs:66-91`) have no visible home, and the macOS menu bar has only the app menu (`crates/app/src/main.rs:141-151`).

**Full menu bar:**

| Menu | Items |
|---|---|
| File | New request, New folder, New collection…, Open collection…, Recent ›, Import…, Reload from disk, Close collection |
| Edit | Undo, Redo, Cut, Copy, Paste, Find in response, Format body |
| Request | Send, Save, Save and close tab, Explain, Compare with previous, Copy resolved URL, Copy as curl, Duplicate, Delete… |
| Environment | Switch list with ⌘1…9, Variables…, New environment…, Secrets storage › |
| View | Sidebar, Layout, History, Cookies, Theme, Zoom |
| Wisp › | Settings…: trust, confirm before send, history bodies, clear history |

Windows and Linux get the same menus in an in-window menu bar (Q4). The palette stays and searches all of them. **Copy as curl is the one new capability in the release.** It is small and cuttable (Q6). It must mask secrets by default, like the URL copy.

**Button system:** primary, secondary, quiet and destructive, in two sizes (32 and 26 px). One primary per area. Icon-only buttons have a tooltip with the name and shortcut. Destructive actions confirm in place.

## Feature 7 — First-run empty state

With no collection open the window shows "Start with a collection": New collection, Open folder, Import (Postman or OpenAPI), and recent collections.

## Feature 8 — Landing site

The mock and the stale 0.3/0.4 roadmap cards on the landing site move to the 0.6.0 look and content at release. It is a separate repository (`~/workspace/wisp-site`), a single task, and outward-facing, so it is done by the user or with their go-ahead.

## Per-user and security invariants

- A secret value never appears in the resolved-URL preview, a token card, a copy action (unless the user chose the reveal path), a screenshot fixture, a log line or a history entry.
- The Secret checkbox's promise holds: a secret is never written to a collection file or history. A move between stores never leaves a secret in both and never drops one on a failed write.
- Tests never touch the real keychain or the user's settings.
- The highlighter reads text only. It runs no code and loads no files.

## Frozen types touched

None planned. The Variables view needs a new read-only core function, not a change to `Request`, `Scope`, `VarSource` or the file formats. The architect confirms this in the first wave. App `Settings` may gain display settings (zoom, layout) additively.

## Size

Size is a goal, not a gate. Every wave's measure step records the Windows GUI and CLI sizes and reports them. A single task that grows the Windows GUI by more than about 250 KB gives a one-line justification in its HISTORY entry. There is no hard stop and no cut order. The 0.5.0 head figure is the baseline (`scripts/measure/results/`). Likely large items: the highlighter (depends on Q1) and any bundled fonts (Q2).

## Waves (proposed, to be fixed by `/plan`)

1. **Foundations:** tokens, spacing and radius scale, button system; the architect spike for Q1 and Q4; the core variable-listing function.
2. **Features in parallel:** body rendering and highlighting; resolved-URL preview and token cards; Variables view; menu bar.
3. **Empty state and integration:** first-run state, screenshots, contrast tests.
4. **Release:** measure, docs, macOS hand checklist, landing-site refresh. The tag, publish and after-action report are the user's.

## Risks

1. **Scope.** This touches most of `crates/app`. Many tasks share `root.rs`, `workspace.rs` and `url_bar.rs`, so the plan must serialise on shared files, as 0.5.0 did.
2. **GPUI limits.** Soft-wrap with line numbers in `EditorState`, in-window menu bars and keyboard-reachable hover cards are unverified. The spikes in wave 1 decide them before features build on them.
3. **Secret leaks through new surfaces.** The preview, the cards, copy actions and screenshots are new places a secret could appear. Each has a test with a known secret value.
4. **Resolver order mismatch.** The UI must state the order the resolver really uses (Feature 5).
5. **Hand testing.** Windows and Linux in-window menus and the light theme are only hand-checkable late (D-I).

## Exit criteria

- Every item under Success holds.
- Each of the eight features is merged or explicitly cut by the user, with the cut recorded.
- The preview-equals-prepared-request test and the secret-masking tests pass; contrast tests cover the new tokens in both themes.
- Windows GUI and CLI sizes are measured per wave and stated in the release notes, with any task over about 250 KB justified.
- No file-format change, or the user has approved one.
- The macOS hand test is done before the tag (D-I), and the release notes say which platforms were tested.
- Docs are updated: README features and screenshots, `docs/architecture.md` (Variables view, tokens, highlighter interface), and the landing site refresh is done or deferred by the user.

## Open questions (answer before `/plan`; recommendation first)

1. **Q1 Highlighting engine.** Enable gpui-component's own highlighter, or write a small in-crate tokenizer for JSON, XML and HTML? Recommendation: decide by an architect spike that measures size and fit; lean towards an in-crate tokenizer for JSON with a trait for the other languages.
2. **Q2 Fonts.** Bundle Inter and JetBrains Mono (as in the mockups), or use the system UI and system monospace fonts? Recommendation: system fonts; the mockup fonts are illustrative.
3. **Q3 Mixed secret storage.** Today one environment can have some secrets in the keychain and some in a file. Should the per-environment setting then show "mixed" with a "Move all to…" action, with reading unchanged? Recommendation: yes.
4. **Q4 In-window menu bar on Windows and Linux.** Does GPUI support one, or do we fall back to a hamburger menu in the top bar? Recommendation: the architect checks; the fallback is acceptable.
5. **Q5 Variables view placement.** A full tab-like view, or a side drawer over the request? Recommendation: its own tab-like view (as in board 2), opened from the top bar, ⌘⇧V and the request's Variables sub-tab.
6. **Q6 Copy as curl.** In or out? Recommendation: in, and cut first if needed.
7. **Q7 Light theme.** Same tokens, both themes hand-checked? Recommendation: yes, with the contrast tests extended to the new tokens.
8. **Q8 Testing.** macOS hand test only (D-I unchanged)? Recommendation: yes, plus screenshots of each board's screen in CI where the existing Linux Xvfb screenshot job can take them.

One further point for the user, not a question the brief asked: the precedence order in the brief differs from the code (Feature 5). This spec uses the code's order.
