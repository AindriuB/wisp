# Wisp 0.3.0 — design spec

Status: agreed 2026-11-14 in a shaping session, from the architect's design plus the user decisions below, on `main` at `7f3f64a` with 0.2.0 about to be tagged. Inputs: the source audit is the user's `PRODUCT-AX-AUDIT.md` (untracked, not committed, cited by name only), the 0.2.0 spec (`2026-11-09-wisp-0-2-0.md`) and the user decisions below. Architectural work; hand to `/plan`. Citations are `path:line` at `7f3f64a`.

## Outcome

Wisp 0.3.0 makes a request explainable and safer to send, without adding scripting or an agent platform. A developer can see where every variable, header, auth setting and request setting of a request came from, close a tab with "save and close", ask for a confirmation before sending to a chosen environment, attach pass/fail assertions to a request, see which environment and checks each history entry ran with, and run read-only `validate`, `inspect` and `explain` from a terminal or an agent through a separate `wisp-cli` binary.

**Success:** all of the above work on macOS, Windows and Linux; the Windows GUI exe stays at or under 15,500,000 B (about 15,181,824 B now, headroom about 318 KB); `wisp-cli` stays inside its own budget; no secret value appears in any explain output, CLI output, history entry or log.

## User decisions (2026-11-14, all binding)

- **Scope:** Explain Request; Save-and-close plus a per-user environment guard; declarative assertions plus history provenance; a read-only `wisp-cli`. Agent collaboration is a side feature of these, not a goal. Deferred: service-layer extraction, change sets, approvals, MCP, CLI `run`, live IPC.
- **Windows GUI gate** stays 15,500,000 B.
- **Assertions:** an additive `[[assert]]` table in request TOML, `format = 1` unchanged. Failure is report-only and never blocks a send. No scripting. Kinds status, header and JSON path, with a minimal operator set. History entries record the environment name and assertion results as names and hashes only, never values; all new fields `serde(default)`. An editor tab in the request editor.
- **Explain:** a read-only inspector of the effective request with provenance (request, folder chain, collection defaults, environment, secret, dynamic) and a pre-send context strip (active environment, auth source, history scope). Explain never reveals a secret value: secrets are shown by name, source and resolved-or-not, and revealing stays in the Environment secrets panel. Dynamic values are marked "generated at send". The core produces a reusable report type that the CLI's `explain` reuses.
- **Save and close:** the close prompt gets Save-and-close; a failed save keeps the tab open and a disk conflict is never overwritten. Check whether the quit prompt should share it. Task 128 fixes the plain Ctrl-S disk-conflict overwrite before the 0.2.0 tag, so Save-and-close builds on the checked save (see 2a).
- **Environment guard:** per-user (in settings, keyed by collection id and environment name), never in the committed environment file. A committed hint may only suggest enabling it. It is a guard against accidents, not a security control.
- **CLI:** `wisp-cli` is a separate console binary in a new crate with no GPUI, with a deny-GPUI boundary check. Commands `validate`, `inspect` (bounded, redacted, dedicated DTOs, never `Serialize` on `Environment`, `PreparedRequest` or history) and `explain`. Plain text by default, versioned JSON with `--json`. No `run`, no network. On macOS it ships inside the bundle at `Wisp.app/Contents/MacOS/wisp-cli`, signed and notarised with the app. On Windows it is signed through SignPath like `wisp.exe`, as a second `pe-file` in the artifact configuration; until the user updates SignPath it ships unsigned with a notice.
- **Constraints:** Everything hand-rolled, no heavy dependencies. Each wave ends with a measure task. The CLI is outside the gate and gets its own budget. `crates/app/src/workspace.rs` (4,822 lines) is the serial hot file. Secrets are never logged or exported. Tests never touch the real keychain.

## Goals and non-goals

**Goals:** the four features above, each testable without a window where the logic allows it; one `ResolutionReport` shared by the GUI and the CLI; additive file-format changes only.

**Non-goals (later, with reasons):**

| Later | Why not 0.3.0 |
|---|---|
| Service-layer extraction from `workspace.rs` (`Workspace::send`, `prepare_send`, history recording, vault coordination) | The audit puts it before any execution interface. 0.3.0 has no execution interface: the CLI cannot send, so the CLI needs only `resolve`-side logic, which already lives in `core` and `storage`. Extracting from a 4,822-line serial file is a release of its own. |
| Reviewable change sets, plan/apply, undo journal | Needs the service layer and revision preconditions; nothing in 0.3.0 mutates a collection except the existing save. |
| Send approval, execution policy, environment safety classes | The 0.3.0 guard is a per-user prompt in the GUI. An enforced policy needs the service layer to be the single send path. |
| MCP adapter | A thin adapter over the service layer and the CLI DTOs; both come first. |
| CLI `run` | Needs the service layer so desktop and CLI behave identically (audit: "a CLI calling only `resolve()` and `Engine` could behave differently"). Also the only reason the CLI would need the network. |
| Live IPC / unsaved-draft visibility | The audit's "agent cannot see an unsaved human draft" needs a transport; the Engine API is already serialisable (`docs/architecture.md:72-74`) but nothing listens. |
| Request IDs (durable) | A cross-request-workflow feature; nothing in 0.3.0 references a request by anything but its path. |
| Import idempotency | Importers add with suffixed names by design (`PRODUCT-AX-AUDIT.md:34`); making them idempotent needs request IDs. |
| Response diff view | Needs stored-body completeness indicators and ignore-lists; the 0.3.0 history fields are a prerequisite, not the feature. |
| Per-request vars editor, `DirtySections.vars` | Explain makes request vars visible read-only; an editor is separate UX work. |
| Variables inside assertion expected values | 0.3.0 expected values are literals (see feature 3); this keeps secrets out of assertions and history by construction. |
| CLI reading the OS keychain (`--keychain`) | 0.3.0 CLI never opens a secret store (no prompts, no ACL surprises in CI). Keychain-backed secrets show as "not loaded by the CLI". |
| Feature-gating `core`'s network code so the CLI links no `reqwest` | See feature 4, option B. |

## Shape

One new crate, `crates/cli` (package `wisp-cli`, binary `wisp-cli`), linking `wisp-core` and `wisp-storage`, no GPUI. Otherwise: report and assertions logic in `core` (pure, no I/O), `[[assert]]` codec, tolerant validation, environment metadata and history fields in `storage`, all UI in `app`. The Engine's `Command` and `Event` types and `PreparedRequest` do not change; assertions are evaluated in the app from data the Completed handler already holds (`crates/app/src/workspace.rs:2592-2602` reads up to `BODY_CAP + 1` bytes of the body and the tab already holds the response headers). `resolve()` stays pure and its source is not restructured (see feature 1).

## Feature 1 — Explain Request

### Behaviour

- **Explain pane.** A new response-pane sub-tab "Explain" beside Body, Headers and Cookies (`crates/app/src/tab.rs:24-28`). It needs no response, so it works before the first send and updates as the draft is edited (while visible). It lists, each with its origin:
  - **Variables** referenced by the request: name, origin (request, folder `<name>`, collection, environment `<name>`, secret `<name>`, dynamic), and the layers that define the same name but lose (shadowed). Unresolved names and expansion errors (cycle, too deep, too large) are listed with the location they were used in.
  - **URL, query params, path params**: the resolved text and the origin of each parameter.
  - **Headers**: each effective header, the layer that set it, the layers it overrode, and synthetic ones named as such ("Content-Type: from body type JSON", "Authorization: from auth Bearer").
  - **Auth**: the effective kind, the layer it was inherited from (request, folder `<name>`, collection, none), how it is applied (header, query, or "at send by the engine" for Digest, SigV4, OAuth2), and each field by name only.
  - **Request settings**: timeout, follow redirects, verify TLS, each marked "request" when it differs from the default and "default" otherwise (`RequestSettings` has no explicit-versus-default flag, `crates/core/src/request.rs:289-305`); the engine default timeout is shown as an app note (`crates/core/src/engine.rs:60`).
  - **Body**: kind, byte length of the resolved text, the variables used. Never the content.
- **Context strip.** One line under the URL row (`crates/app/src/ui/url_bar.rs`), always visible: active environment (name, and whether its secrets loaded, failed, or are keychain-backed), auth source ("Bearer, from folder users"), history scope ("records under `users/get-user.toml`", "scratch: recorded without a request link", "off: <reason>"). History scope comes from `scope_path_for` (`workspace.rs:662-686`) and the collection's history state, which prepare_send uses to change scope when a from-history tab's URL is edited or its original is gone (`workspace.rs:1104-1138`); today this is only explained after the send, in the Resend notice.
- **Display rules.** A value is shown only if it is not secret-derived, its field or variable name is not credential-like (`wisp_core::redact::is_credential_name`, `crates/core/src/redact.rs:32-35`), and it is at most 200 characters (the existing hover limit, `crates/app/src/highlight.rs:119`). A secret-derived part is shown as `secret NAME (resolved)` or `secret NAME (not set)`; a dynamic part as `$uuid, generated at send`; a masked part as `hidden: credential name`. Resolving is never repeated for display: dynamic values are not generated.

### Data model (`core`)

New file `crates/core/src/resolve/report.rs`, re-exported from `resolve/mod.rs` (currently `mod.rs:85`).

- `ResolutionReport` (plain data: `Debug`, `Clone`, `PartialEq`; **no `Serialize`**, so the CLI cannot dump it by accident) with: environment (name, per-secret `{name, present}`), method, URL, params, headers, auth, settings, body, variables, problems and warnings (names and locations only; reuse `Problem` and `Location`, `resolve/mod.rs:15-33`).
- Display text is a `Shown` value made of typed parts: `Text`, `Secret{name, resolved}`, `Dynamic{name}`, `Hidden`. Typed parts, not sentinel characters in a string, because a user value can contain any text. The invariant is structural: **a secret's value is never copied into the report**; the expander emits `Secret{name, resolved}` where it meets a secret-sourced variable and does not expand the secret's value at all.
- `Origin`: `Request`, `Folder(index)`, `Collection`, `Environment`, `Secret`, `Dynamic`, `BodyType`, `Auth`. Folder is an index into `Scope::folders` (outermost 0), exactly like `VarSource::Folder` (`engine.rs:77-84`); renderers map it to a folder name, as `hover_text` already does with `folders: &[String]` (`highlight.rs:121-137`) and `url_bar::folder_names` (`url_bar.rs:38`).
- Entry point `explain(&Request, &Scope) -> ResolutionReport`, plus a cheap `explain_auth(&Request, &Scope)` for the always-visible strip (the strip must not build the full report per keystroke).

### Implementation approach and why

`explain` is a separate walker in `report.rs`, not a mode inside `Resolver`. It reuses `lookup` (made `pub(super)`) and adds `lookup_all` (every layer that defines a name, for shadowing); it mirrors the header layering (`merged_headers`, `engine.rs:442-458`), the auth choice (`apply_auth`, `engine.rs:463-474`) and the expansion bounds (`MAX_DEPTH`, `MAX_OUTPUT`, `MAX_EXPANSIONS`, `engine.rs:19-26`, made `pub(super)`).

- *Why not add a trace mode to `Resolver`:* `resolve()` runs per keystroke for the URL preview (`docs/architecture.md:91-97`) and its tests are 764 lines (`resolve/tests.rs`). Threading a sink through `expand` puts the hot pure path at risk for a display feature.
- *Cost:* the layering and bounds logic exist twice. **Mitigation, mandatory:** a parity test that runs every fixture of `resolve/tests.rs` through both and asserts that, for non-secret, non-dynamic fixtures, the flattened report text equals the `resolve()` output field by field, headers included. Drift fails the build.
- `VarLookup` and `lookup_var` (`engine.rs:86-160`) and `hover_text` (`highlight.rs:121-158`) are unchanged in 0.3.0. Unifying hover onto the report is a later cleanup.
- Frozen type touched: none. `VarSource` stays as is; `Origin` is new.

### Security and redaction

- No secret value in any report string, by construction (above). Test with a canary: an environment secret whose value is a unique marker, used directly, nested in a plain variable, in a header, in the URL query and in auth; assert the marker is in no field of `format!("{report:?}")` and `{:#?}`.
- Credential-named headers, params, variables and auth fields are always `Hidden` even when the value is a plain literal, so a token pasted into a committed header is not echoed to the CLI's reader.
- URL userinfo is `Hidden` (reuse the logic of `redact_userinfo`, `crates/core/src/model.rs:72-78`, made `pub(crate)`).
- `ResolutionReport` is not `Serialize`; the CLI maps it to its own DTOs (feature 4).

### Tests

Parity test (above); canary test; precedence tests (request over folder over environment secret over environment plain over collection, shadowing lists the losers); dynamic marked and never generated (assert no UUID-shaped text); header layering and Content-Type synthesis; inherited auth names the right folder; unresolved, cycle and too-deep show as problems. App: a pure function builds the strip text from (report, `scope_path_for` result, history state), tested without GPUI.

### Size estimate (Windows GUI exe, estimated from line counts at about 30-70 B per line; confirmed by the wave measure)

`report.rs` about 450 lines and engine hooks about 25: +12 to 20 KB. App `ui/explain.rs` and the strip: +35 to 55 KB. Total +50 to 75 KB.

## Feature 2 — Save and close, and the environment guard

### 2a. Save and close

**Today.** Three prompts say "Discard unsaved changes?" with `["Discard", "Cancel"]`: close a tab (`crates/app/src/ui/root.rs:50-62`, the user's `:58-60`), close a collection (`root.rs:472-490`, the user's `:481-483`; this one is the collection close, not a tab close), and quit (`crates/app/src/main.rs:106-130`). `Discard` is index 0, so it is also the default button. Saving is `Workspace::save` (`workspace.rs:2840-2873`). Three-button prompts already exist (`crates/app/src/vault.rs:846-856`), so the prompt API supports them; per-platform behaviour is covered by the hand test.

**Behaviour.** The tab-close prompt becomes `["Save and close", "Discard", "Cancel"]`, with Save first so the default is the safe choice. Save-and-close saves, and closes only if the save succeeded and the tab is clean afterwards. The same helper serves the other two prompts, as "Save all and close" (collection) and "Save all and quit" (quit): recommended, because the helper is the same and a user who sees Save in one prompt expects it in the others. Quit stays a no-op on any failure.

**Invariants and where each is enforced (new code unless cited):**

1. *A failed save keeps the tab open.* The helper closes only after `save` returned `Ok` **and** the tab is no longer dirty. The second check is needed because `Workspace::save` returns `Ok(())` without saving when no collection is open (`workspace.rs:2841-2844`), which would otherwise close a dirty scratch tab and lose it.
2. *A disk conflict is never overwritten.* Refuse when the tab's `DiskState` is not `InSync` (`crates/app/src/tab.rs:36-41`). Because the watcher can lag (100 ms coalescing, `docs/architecture.md:109`), also re-read at write time: a new `storage::request::save_request_if_unchanged(path, expected_saved, draft)` loads the file, compares it with the tab's `saved` snapshot, and returns a `Conflict` error without writing on any difference or if the file is missing; it writes through `save_request` otherwise. A conflict sets the tab's disk state to `ChangedOnDisk` and keeps it open, so the existing banner (`root.rs:546-575`) takes over. There is still a window between that read and the atomic write; it is narrower than the watcher's but not zero, and the spec does not claim otherwise.
3. *Scratch tabs.* A new tab saves through `create_request`, which picks a fresh name (`workspace.rs:2852`); it cannot clobber. With no collection open, Save-and-close is not offered (the prompt keeps Discard and Cancel plus a notice "Open a collection to save").
4. *No second prompt while one is up.* The existing `prompt_up` flag and `has_active_prompt()` guard is reused (`root.rs:50`, `main.rs:107`); the helper clears `prompt_up` on every path.
5. *Save-all stops at the first failure* and reports which tab failed; nothing is closed after it (quit and collection close are all-or-nothing).

**Plain Save and task 128.** At `7f3f64a`, plain Save (`on_save`, `root.rs:416-421`) does not look at `DiskState`: with the "Changed on disk" banner showing, Ctrl-S overwrites the file. Task 128 fixes this before the 0.2.0 tag. Save-and-close in 0.3.0 builds on that checked save and must reuse whatever 128 lands, not add a second check beside it. `save_request_if_unchanged` above is the re-read-at-write-time step; the 2E task must read 128's result first and fold the two together rather than duplicate them. See open question 1.

**Placement.** Pure decision logic and prompt specs in a new `crates/app/src/save_close.rs` (button mapping, "what happens after the save result", testable without GPUI). `crates/app/src/ui/root.rs` and `main.rs` call it. One new method on `Workspace` (about 35 lines, `workspace.rs`) does the checked save, because `owner_of` and `root_of` are private (`workspace.rs:1340,1352`). `close_step` and `quit_step` (`workspace.rs:1280`, `main.rs:~100`) are unchanged.

**Tests.** Pure: all button/result combinations (save ok, save error, conflict, scratch without collection, still dirty after save). Storage: `save_request_if_unchanged` with an unchanged file, a modified file, a deleted file, a sidecar body changed by another process. GPUI test-support for the tab-close flow if the existing tests do this for `close_step` (`workspace.rs:3631-3645` are pure); otherwise hand-checked in the wave hand test.

**Size:** +8 to 15 KB.

### 2b. Environment guard

**Behaviour.** For a guarded (collection, environment), Send asks "Send to <environment>?" with the method and URL host, and does nothing on Cancel. Guarded sends include Resend from history (same `send` path). It does not guard OAuth Authorize (token requests, `workspace.rs:~2411`) and says so in the docs. Toggling: a palette command "Toggle confirm before send (this environment)" and a click on the guard badge in the context strip. Enabling for a collection with no id yet creates the id through the existing path (`resolve_id_then`, as the first Send does, `workspace.rs:2295-2309`); a guard cannot exist without an id.

**Storage (per user, `settings.toml`).** A flat array, matching how `open_collections` is stored (`crates/app/src/settings.rs:149-156, 238-263`):

```
confirm_send = ["6f1c2d1e-....:production", "6f1c2d1e-....:staging-eu"]
```

Each entry is `<collection-id>:<environment-name>`; split at the first `:` (a collection id is a UUID, so it has none). The key is absent when empty. A new field `confirm_send` on `Settings` (`settings.rs:22-34`), kept as a sorted set so `Settings` stays `Eq`. It is never in `collection.toml` or `environments/*.toml`.

**Committed hint.** Optional top-level `suggest_confirm = true` in `environments/<env>.toml`, beside `secrets = "keychain"` (`crates/storage/src/vault.rs:255-269` is the precedent). Read by the environment loader into `LoadedEnvironment` (`vault.rs:401-411`, one construction site) and shown once as a notice "This environment suggests confirming sends. Enable?" It never enables the guard by itself and cannot disable one. Older versions ignore the key (additive; `format` is not part of environment files).

**Invariants.**

1. *The confirmed environment is the environment sent to.* After the prompt returns, the helper re-reads the active environment; if it changed while the prompt was up, it aborts and re-prompts. Without this, switching environments with the prompt open sends to a different environment than the one confirmed.
2. *Fail-open is bounded and stated.* A rename of the environment drops the guard (it is keyed by name); a collection whose id is not yet `Known` (`workspace.rs:262-273`) has no guard. This is an accident guard (user decision). The settings UI says "set per user; a renamed environment loses it".
3. *One choke point.* Both interactive send paths call one helper: `url_bar.rs:303-310` (the Send button, which currently discards errors) and `root.rs:405-413` (the keyboard action). The guard helper lives in `crates/app/src/guard.rs` (pure `needs_confirm(settings, collection_id, env_name)` plus the prompt glue). `Workspace::send` is not changed, so the autosend harness (`workspace.rs:1461-1471`, a scratch tab with no environment) is not affected.

**Workspace.rs edits:** one read accessor for a collection's known id (about 8 lines) and the `suggest_confirm` plumbing in the environment-load completion (about 8 lines). Both are in the serial queue (see Waves).

**Tests.** Pure `needs_confirm` table; settings round-trip including a malformed entry (dropped with the existing "bad key" notice, `settings.rs:143-146` pattern), a collection id with no environment, an environment name containing `:`; the environment-switched-during-prompt abort; hint parse (present, absent, wrong type is ignored with a notice, not fatal).

**Size:** +6 to 12 KB.

## Feature 3 — Assertions and history provenance

### Behaviour

- **Editor.** A new request sub-tab "Assertions" after Settings (`crates/app/src/tab.rs:14-21`, `crates/app/src/ui/request/mod.rs:27-34`): add, remove, reorder, edit kind, target (header name or JSON path), operator and expected value; an inline error for an invalid regex or path. Unrecognised entries (written by a newer Wisp) are shown read-only and kept.
- **Result.** After a send that got a response, a "Checks" sub-tab in the response pane (new `ResponseSubTab`) lists each assertion with pass, fail or skipped; a fail shows expected and the actual value, truncated to 80 characters, in the pane only. The status line shows "3/4 checks". A failed assertion changes nothing else: the send completes and is recorded.
- **No response, no results.** A failed or cancelled send has no results; the history entry has an empty list.
- **Limits:** at most 50 assertions per request; regex patterns at most 256 characters, compiled with a size limit; JSON path at most 256 characters and 16 segments; JSON assertions run only on a body of at most 1 MiB (`BODY_CAP`, `crates/storage/src/history.rs:23`, which the Completed handler already uses), otherwise "skipped: body over 1 MiB". The body is parsed once for all JSON assertions.

### File format (exact TOML; additive, `format = 1` unchanged)

```
[[assert]]
kind = "status"
op = "equals"
value = 200

[[assert]]
kind = "header"
name = "content-type"
op = "contains"
value = "json"

[[assert]]
kind = "json"
path = "$.data.items[0].id"
op = "exists"

[[assert]]
kind = "json"
path = "$.data.state"
op = "matches"
value = "^(ready|done)$"
```

Validity matrix (anything else is a malformed assertion):

| kind | target | operators | value |
|---|---|---|---|
| `status` | none | `equals`; `matches` | integer 100-599; regex over the three-digit status text |
| `header` | `name` (case-insensitive) | `equals`, `contains`, `matches`; `exists` | string; `exists` takes an optional boolean, default true |
| `json` | `path` | `equals` (string, integer, float or bool, compared by type); `contains` (substring of a string value, or an equal scalar element of an array); `matches` (string values only); `exists` | typed TOML scalar; `exists` as above |

- Header with several values of the same name: `equals`, `contains` and `matches` pass if any value passes.
- Hand-rolled JSON path subset: `$`, `.name`, `['name']` and `[n]` (non-negative index). No wildcards, filters, recursion, slices or negative indexes: each can match several nodes, and the minimal set must give one answer. JSON `null` cannot be an expected value (TOML has none); use `exists`.
- `matches` uses the `regex` crate already in `core` (`crates/core/Cargo.toml`, used at `crates/core/src/resolve/engine.rs:415`); it is linear-time, so a hostile pattern cannot stall the UI thread, and the size limit bounds compile cost.
- **Expected values are literals.** A `{{var}}` in an expected value is not expanded; the editor and `validate` warn on `{{`. This keeps secrets out of assertions, history and the stored request copy by construction, at the cost of not asserting against a variable. Revisit later with the service layer.
- **Forward compatibility.** An `[[assert]]` table with an unknown `kind` or `op` is loaded as an `Unrecognised { raw TOML text, reason }` entry, not an error: the request still opens, evaluation reports it "skipped: not supported by this version", and `save_request` writes its raw text back verbatim, so opening and saving a request authored by a newer Wisp does not delete its assertions. A malformed known kind is the same variant with reason "malformed", flagged by `validate` as an error. Saving never drops an entry.
- Older versions (0.2.0) ignore the key on load, and keep it on save because `save_request` edits the document in place (`crates/storage/src/request.rs:329-370`; it only rewrites the keys it knows). A fixture test proves this against the 0.2.0 code path (a request with `[[assert]]` round-trips byte-for-byte through a save that changes only `url`).

### Data model

- `core`: new module `crates/core/src/assert.rs`: `Assertion` (`Status`, `Header`, `Json`, `Unrecognised`), `Op`, `Expected`, `AssertionResult { label, verdict }`, `Verdict { Pass, Fail { actual: Option<short text> }, Skipped { reason } }`, `Assertion::label()` (such as "status equals", "header content-type contains", "json $.data.id exists") and `Assertion::fingerprint()` (first 8 bytes of SHA-256 over kind, target, op and expected, as 16 hex characters; `sha2` is already a `core` dependency). Pure `evaluate(&[Assertion], &Facts { status, headers, body: Option<&[u8]> }) -> Vec<AssertionResult>`. `AssertionResult` has a hand-written `Debug` that omits the actual value, with a `debug_redacts_*` test for `{:?}` and `{:#?}` (`docs/conventions.md:62-70`).
- `Request` (`crates/core/src/request.rs:307-320`) gains `assertions: Vec<Assertion>`, `serde(default)`. History's stored request copy gets it cleared (below).
- `storage`: `codec.rs` reads and writes the `[[assert]]` array-of-tables (writes only when non-empty or when the file already has the table, the same "keep what exists" rule `save_request` applies to `[auth]`, `request.rs:347-349`); `load_request` and `save_request` call it.
- `HistoryEntry` (`crates/storage/src/history.rs:162-190`) gains `environment: Option<String>` and `assertions: Vec<AssertionRecord>`, both `serde(default)`. `AssertionRecord { label, hash, state }` with `state` one of pass, fail, skipped. `NewEntry` (`history.rs:196-208`) gains the same two fields.

Example history index line fragment (additive keys, older readers ignore them):

```
"environment":"production","assertions":[{"label":"status equals","hash":"a1b2c3d4e5f60718","state":"pass"}]
```

### Redaction rules for history

- Store: environment name (not secret; `PreparedRequest.environment` already carries it, `crates/core/src/model.rs:59-61`), each assertion's label (kind, header name or JSON path, operator), its definition fingerprint, and the state. **Never** the expected value, the actual value, or a hash of an actual value.
- *Why the hash is of the definition and not of the response value:* a hash of a low-entropy response value (a status code, a flag) is trivially reversible, and a hash of a token is still a stable identifier of it. The definition fingerprint lets a later reader see that an assertion changed between two runs without learning anything the committed request file does not already say.
- `redact_request` (`history.rs:296-340`) sets `assertions` to empty in the stored request copy, so the `.req.json` file carries no expected values. **Cost:** Resend from history re-runs no assertions, because the stored copy has none; the entry's own record shows what ran. The Resend notice (`crates/app/src/ui/history.rs:60-90`) says "assertions are not resent".
- The label can contain a JSON path or header name taken from the request file; those are authored identifiers, subject to the same 200-character cap as other displayed names.

### Placement and `workspace.rs` edits

## Feature 4 — Read-only CLI (`wisp-cli`)

### Commands and output

```
wisp-cli validate <collection> [--json]
wisp-cli inspect  <collection> [--env <name>] [--json]
wisp-cli explain  <collection> <request-path> [--env <name>] [--json]
wisp-cli --version | --help
```

- `<collection>` is an explicit path to a folder with `collection.toml`; no current-directory search and no environment variable, so an agent states what it reads. `<request-path>` is relative to the collection root. `--env` is optional; without it the output says "environment: none" and lists the environment-sourced variables as unresolved.
- Plain text by default. `--json` prints one document per command: `{"schema":"wisp-cli/1","command":"explain", ...}`. Additive fields do not bump the schema; a removal or a type change does. Exit codes: 0 success, 1 `validate` found errors, 2 usage error, 3 the collection or request could not be read. `explain` exits 0 when the request exists, even with unresolved variables (they are the report); a future `--strict` can change that.
- **`validate`:** a new tolerant walker, `crates/storage/src/validate.rs`, returns every finding (path, key, message, severity) instead of stopping at the first, because `open_collection` returns on the first bad `folder.toml` (`crates/storage/src/collection.rs:~345`, `load_folder_defaults(&abs)?`). It checks `collection.toml` (including `format`, `UnsupportedFormat`), every `folder.toml`, every request file through `load_request` (so sidecar bodies, auth, settings and `[[assert]]` are checked), every environment file through `load_environment`, and lists `Node::Invalid` entries. The tolerant walk is in `storage`, not the CLI, so the GUI can use it later.
- **`inspect`:** a bounded structure from dedicated DTOs: collection (id if present, format, counts); environments (name, secrets mode, variable names, secret names, never a value); the tree up to 2,000 nodes with `truncated: true` after that (path, kind, name, method, URL origin and path without query, auth kind, header names, assertion count, valid flag); names capped at 200 characters. Plain variable values are not printed either: a plain variable named `token` is still a value in a committed file (see the redaction rules).
- **`explain`:** `explain(&Request, &Scope)` from `core` over `open_collection` + `scope_for` + `load_request` + the environment, then a DTO mapping of the report. Text output is the same sections as the GUI pane.

### Crate and module layout

`crates/cli`: `main.rs` (argument parsing, exit codes), `args.rs`, `dto.rs` (all `Serialize` types, schema version), `output.rs` (text and JSON writers), `cmd/{validate,inspect,explain}.rs`. Dependencies: `wisp-core`, `wisp-storage`, `serde`, `serde_json`, all already in the lock; no new third-party crate, so `THIRD-PARTY-NOTICES` does not change (it is generated from the app manifest, `scripts/notices/generate.sh:~24`, and the CLI's tree is a subset). `[[bin]] name = "wisp-cli"`; console subsystem (no `windows_subsystem` attribute, unlike `wisp.exe`, `docs/architecture.md:290`; this is the reason for a separate binary).

### Argument parsing: hand-rolled

Recommended: hand-roll over `std::env::args_os`, about 150 to 250 lines (+5 to 10 KB). The grammar is three subcommands, one positional or two, and three flags. **Buys:** no dependency, consistent with the workspace rule, full control of exit codes and of the text of usage errors. **Costs:** usage text and `--flag=value` and `--` handling are ours to test; a table-driven test covers them. The alternative, `lexopt` (a small, dependency-free tokenizer, estimated +10 to 15 KB, GUESS: not measured), saves only the tokenizing. Switch to it if subcommands exceed about five or flags exceed about ten, which `run` would likely cause.

### Redaction and read-only rules

1. **DTOs only.** `dto.rs` defines every serialisable type; `output.rs` has one generic emit function bounded by a sealed `Dto` trait implemented only in `dto.rs`. No `Serialize` on `Environment` (it derives it today, `crates/core/src/request.rs:371`), `PreparedRequest` (`model.rs:47`), `HistoryEntry` or `ResolutionReport`. A reviewer adding `impl Dto for Environment` is visible in a diff.
2. **Secrets never enter the process in usable form.** The CLI loads environments with `storage::environment::load_environment`, which reads `*.secrets.toml` only for file-mode environments and yields no secrets for keychain-backed ones (`crates/storage/src/environment.rs:146-175`). It replaces every secret value with a fixed placeholder before building the scope. The report never carries values anyway; this is defence in depth, so a bug cannot print what the process never held. The CLI never constructs a secret store, never calls `keychain::open`, and so never touches the OS keychain; keychain-backed secrets are reported "keychain: not loaded by the CLI". (`load_environment_with` with `NoStores` would silently fall back to the file, `vault.rs:452-460`, which is wrong here, hence `load_environment`.)
3. **Names and structure only.** `inspect` prints no variable value, header value, body or URL query. `explain` follows the display rules of feature 1.
4. **Read-only.** The CLI never calls `ensure_collection_id`, `save_*`, `create_*`, `atomic_write*`, `ops::*`, or opens the history store or the per-user data dir. A collection without an id is reported as having none; it is not given one. Test: copy a fixture to a temp dir, make it read-only, run all commands, assert the file tree and mtimes are unchanged.
5. **Errors print path, key and message** from `StorageError` (`crates/storage/src/error.rs:7-35`). The TOML parse error carries a line number and the parser's short message, not the source line (`crates/storage/src/codec.rs:42-56`). The CLI task must still grep the `invalid(..)` call sites for interpolated values; the two found interpolate a method name and a sidecar file name (`storage/src/request.rs:99, 210`), not secrets.
6. **No logging backend.** The CLI installs no `tracing` subscriber, so `debug!` calls such as `crates/storage/src/vault.rs:~431` print nothing.
7. **Broken pipe.** The release profile is `panic = "abort"` (`Cargo.toml:15`); `println!` on a closed pipe panics. The CLI writes through `writeln!`, treats `BrokenPipe` as a normal exit, and has no `unwrap`.
8. **Canary test:** a fixture with a secrets file value, a plain variable named `api_token`, an `Authorization` header literal and a keychain-mode environment; run every command in both formats and assert the canary strings are in neither stdout nor stderr.

### Boundary check

New `scripts/check-boundaries.sh`, run by `ci.yml` (`check` job, Linux leg only). Today the rule "only `crates/app` may depend on GPUI" (`docs/architecture.md:177-178`) has no enforcement in the repository; this script adds it for all non-app crates:

1. `cargo tree -p <crate> -e normal,build --locked` for `wisp-core`, `wisp-storage` and `wisp-cli` contains none of `gpui`, `gpui-component`, `gpui-platform`, `gpui-pre`, `gpui-pre-platform`, `winresource`.
2. `crates/cli/src` contains none of `Engine`, `Command::`, `reqwest`, `tokio`, `std::net`, `keychain`, `ensure_collection_id`, `atomic_write`, `fs::write`, `create_dir` (read-only and no-network enforced by source check).
3. Optional on the release job: the Linux `wisp-cli` binary's `readelf -d` NEEDED list is a subset of libc, libm, libgcc_s and the loader (GUESS: expected from a build that links none of the GUI libraries; confirm on the first measure).

**Network is excluded by code, not by linkage.** `wisp-core` still depends on `reqwest` and `rustls` (`crates/core/Cargo.toml`), so the CLI links the network stack's types; link-time garbage collection should drop the unreferenced Engine code but that is not a guarantee. *Option B*, feature-gating the `engine` and `auth` I/O modules of `core` behind a default-on feature so `wisp-cli` builds without `reqwest`, `hyper` or `tokio` in its tree, would make "no network" checkable with `cargo tree`. It buys a proof and a smaller binary and costs a `core` module-graph refactor (`Event` carries `BodyHandle`, `Auth` has OAuth2 variants) plus `default-features = false` plumbing through `workspace.dependencies`. Not recommended for 0.3.0; revisit before CLI `run` (which wants the network anyway) or if the first measure shows the CLI over budget.

## Risks

1. **GUI size.** The estimate is 145 to 230 KB against about 318 KB; the assertions editor is the largest piece and the least certain (GPUI-heavy code). Mitigation: the soft line and cut order above; wave 2M is the first real measure, so 2C should land before 2B if one must slip.
2. **Explain drift.** A second walker beside `resolve()` can disagree with it. Mitigation: the parity test over `resolve/tests.rs` fixtures; a failure blocks merge.
3. **`workspace.rs` contention.** Four edits across three waves; any other in-flight task on that file breaks the serial order. Mitigation: the edits are small and listed per task; 2A absorbs the accessors so 2B, 2C and 3A need none.
4. **Guard false confidence.** Keyed by name, per user, lost on rename, not applied to Authorize. Mitigation: wording in the UI and docs; user decision already frames it as an accident guard.
5. **Forward compatibility of `[[assert]]`.** A bug in the verbatim round-trip would delete a newer version's assertions. Mitigation: the fixture test; unrecognised entries are kept as raw text and never re-serialised from the model.
6. **Release packaging.** SignPath configuration is owner-controlled; macOS nested-binary signing and the winget two-portable question are unverified. Mitigation: the 3M dry run is the first proof; fall back to an unsigned or alias-less CLI and say so in the release notes.
7. **CLI links the network stack.** No network is excluded by code review and a source deny-list, not by the dependency tree (option B above).
8. **From-history tabs with `adjustments`.** Not checked whether Save-and-close on a Resend tab (path `None`, redacted body) should be offered; the planner's 2E task must read `HistoryOrigin` (`crates/app/src/tab.rs:~107-130`) before deciding.
9. **Panic abort.** The release profile aborts on panic (`Cargo.toml:15`); the CLI and the new evaluators must not `unwrap` and must bound input (regex size, JSON size, node counts), which the limits above do.
