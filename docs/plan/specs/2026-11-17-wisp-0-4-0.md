# Wisp 0.4.0 — design spec

Status: AGREED 2026-11-17; next step is `/plan`. Scope is the roadmap's 0.4.0 section (`docs/plan/roadmap.md:147-161`) and the decided items D-E, D-F, D-G, D-1 and D-I (`roadmap.md:198-211`); this spec does not reopen them. Inputs: the roadmap, the 0.3.0 spec (`docs/plan/specs/2026-11-14-wisp-0-3-0.md`), task 99's hardening ACs (`docs/plan/tasks/99-hardening-0-2-0.md`). Citations are `path:line` at `ec6b0a4` (0.3.0 released). Guesses are marked GUESS.

## Outcome

Wisp 0.4.0 gives the desktop app and the terminal one send path. A saved request can be run from CI with `wisp-cli run`, which sends it through the same code the GUI uses, evaluates its `[[assert]]` checks, and exits with a code that says which of these happened: it passed, an assertion failed, the HTTP status was not the expected one, the transport failed before anything was sent, or the outcome is unknown. A request file can carry a `description` and an `expected_status`. An agent or a person can print a bounded, redacted snapshot of a collection's persisted state. The GUI gains an editor for per-request variables. The deferred hardening themes H2-H7 and H9 close.

**Success:** GUI and CLI both send through one service function (grep check below); `run` exit codes as in the table below, each covered by a test; `outcome_unknown` documented and tested; every AC listed under H2-H7 and H9 closed; no secret value in any `run` or `snapshot` output, history entry or log (canary tests); the Windows GUI exe stays at or under 16,000,000 B; `wisp-cli` within its (possibly raised) budget; macOS hand test before the tag (D-I).

## User decisions (binding; roadmap ids)

- **D-E** 0.4.0 leads with the service-layer extraction (behaviour-preserving), then `wisp-cli run` with distinct exit codes for transport failure, assertion failure and HTTP status, `outcome_unknown`, and no auto-retry of POST; then E3, C3 as a static redacted export, A4, D3, hardening H2-H7 and H9.
- **D-F** `run` never prompts for secrets by default. `--keychain` opts in to the OS keychain.
- **D-G** No MCP, change sets or approvals. `wisp-cli --json` is the agent interface.
- **D-1** Windows GUI gate 16,000,000 B, soft line 15,900,000 B.
- **D-I** Mac-first release testing: tag after the macOS hand test; release notes say which platforms were tested.
- Decided 2026-11-17 (user accepted the recommended answers to the six open questions):
  - The `wisp-cli` limit is pre-approved to rise to 6 MiB (6,291,456 B) per target if the post-`run` measure (2M) shows any target over 3.6 MB.
  - `run` writes history only with `--history`; off by default.
  - With no `expected_status`, any status below 400 passes.
  - Dynamic values stay one per occurrence.
  - Importers fill `description` from Postman and OpenAPI inside the H4 task.
  - `run` takes one request per call; folder runs are deferred.
- Decided 2026-11-17: Delivery: the engine follows every redirect itself while `follow_redirects` is on (all methods) and sets a fail-closed `nothing_sent` on `Event::Failed`; at most 9 hops, no loop detection beyond the limit (design pass after three external review findings).
- Register verdicts: D3 is `description` and `expected_status` only, file + CLI + read-only in Explain, no GUI editing (`roadmap.md:65`). C3 is `wisp-cli snapshot` only, no live IPC (`roadmap.md:51`). E4 is scoped to `run` and the history result vocabulary (`roadmap.md:74`).

## Goals and non-goals

**Goals:** one send/prepare/history path in a GPUI-free crate that both binaries link; `run` as a CI-grade command; additive file-format and history changes only (`format = 1` unchanged); all hardening ACs above closed.

**Non-goals (later, with reasons):**

| Later | Why not 0.4.0 |
|---|---|
| Folder or collection runs in one `run` call | One request per call keeps the exit-code contract simple; a shell loop covers CI today. Decided 2026-11-17 (user decisions). |
| Printing the response body from `run` (`--body`) | Not in the decided scope; a body can hold session tokens and needs its own output rules. Candidate for 0.5.0. |
| Assertion actual values in CLI output | CI logs are shared; the GUI shows actuals in the pane only (0.3.0 feature 3). `run` prints label, state and skip reason. |
| Retries of any kind in `run` | E4: no auto-retry of unsafe writes. `run` never retries; it reports `retry_safe` for the caller to decide. |
| Enforced send policy in `run` (the GUI's per-user confirm guard) | The guard is a GUI accident guard in `settings.toml` (0.3.0 2b). An enforced policy is C5b, deferred. Docs say `run` ignores it. |
| OAuth2 authorization code in `run` | Needs a browser. `run` fails with exit 4 and says so. Client credentials work. Refresh tokens are held in memory only. |
| GUI editing of `description` and `expected_status` | Register: GUI editing deferred; display only. |
| Live IPC, unsaved-draft snapshot | C3 live part deferred (`roadmap.md:51`). |
| Persisted cookies in `run` | `run` uses a fresh in-memory jar per call and writes no cookie file. |

## Shape

One new crate, `crates/service` (package `wisp-service`, lib `wisp_service`), depending on `wisp-core` and `wisp-storage`, never on GPUI. Both `wisp-app` and `wisp-cli` depend on it.

*Why a new crate and not `app`, `core` or `storage`:* the service must be linked by `wisp-cli`, and only `app` may touch GPUI (`docs/architecture.md:222-226`), so it cannot live in `app`. `core` holds pure resolve and engine I/O and does not know collections, environments on disk or history; putting history recording there would give `core` a dependency on `storage` (the reverse of today's edge). `storage` is file I/O and must not start an engine. A thin crate above both keeps every existing edge. Cost: one more workspace member, one `cargo tree` entry in `scripts/check-boundaries.sh`, and an explicit `[profile.release.package.wisp-service] opt-level = "z"` entry, because `package."*"` does not apply to workspace members (`Cargo.toml:18-25` lists `wisp-core` and `wisp-storage` explicitly for that reason).

What stays in `app`: everything that touches `Context`, `Entity`, tabs, notices, id waits and routes (`Workspace::send` keeps its id-wait path, `crates/app/src/workspace.rs:2523-2595`). The Engine's `Command`, `Event`, `ErrorKind` and `PreparedRequest` do not change.

### Implementation approach and why

- **Lift, then rewire.** Each function moves with its body unchanged, then `Workspace` calls it. `Workspace::send` keeps lines `:2528-2560` (tab reads, pending check, notice on refusal) and calls `plan::prepare` and, in `submit_plan` (`:2597`), `send::submit`. `on_event` (`:2789`) keeps the tab-state updates and calls `outcome::finish` at the terminal event; `append_history` keeps the spawn and calls `history::record`.
- **AC52.** `history::record` takes the `CollectionId` the workspace already holds (`IdState::Known`, as cookies do, `workspace.rs:651-660`). The id is never re-read from disk on append. When the id is not yet known the existing `resolve_id_then` path (`:3523`) resolves it first, as today. Test from the AC: change the id on disk after open; the entry lands in the original store.
- **AC51.** A corrupt cookie file's parse error maps to a fixed message with line and column only (`crates/storage/src/cookies.rs:197` load path; logged at `workspace.rs:3582`). The storage half is a parallel wave 1 task; the `workspace.rs` half is in 1B.
- **AC75.** The test `Workspace::new` must not resolve the real data dir (`workspace.rs:1529` calls `DataDir::resolve()`); 1B owns `workspace.rs`, so it takes this AC.
- *Why not a trait object "SendService" with GUI and CLI implementations:* two implementations are exactly what C1 removes. Free functions over plain data are testable without GPUI and leave the event loop where it is (GUI: `on_event`; CLI: a blocking receive loop in `run.rs`).

## Feature 2 — `wisp-cli run` (C2b, E4, D-F)

### Command

```
wisp-cli run <collection> <request-path> [--env <name>] [--keychain] [--history] [--json]
```

- Arguments as `explain` (explicit collection path, request path relative to its root).
- `--keychain`: load keychain-backed environment secrets through `wisp_service::vault::KeychainStores` (D-F). Without it, a keychain-mode environment yields no secrets and a request that uses one fails with exit 4 and the message "secret NAME is in the keychain; pass --keychain". File-mode secrets (`*.secrets.toml`) load as the GUI loads them. No prompt is ever shown by `wisp-cli` itself; the OS may show its own keychain prompt after `--keychain` (macOS ACLs are per binary; GUESS: `wisp-cli` inside the bundle gets a first-use prompt for items Wisp.app created).
- `--history`: append one history entry, as the GUI would, only when the collection already has an id (`read_collection_id`, never `ensure_collection_id`). No id: the result says `history: skipped (collection has no id)`. Default off (user decision 2026-11-17).
- Parsing stays hand-rolled (`crates/cli/src/args.rs`): five subcommands and six flags are under the 0.3.0 switch threshold for `lexopt` (0.3.0 spec feature 4).

### Exit codes

| Code | `result` | Meaning | Request reached the server? |
|---|---|---|---|
| 0 | `passed` | Response received; status acceptable; no assertion failed (skipped ones do not fail) | yes |
| 1 | `assertion_failed` | Response received; status acceptable; at least one assertion failed | yes |
| 2 | (usage) | Bad arguments (unchanged, `crates/cli/src/main.rs:16`) | no |
| 3 | (unreadable) | Collection, request or environment cannot be read or parsed; `--env` names no environment (unchanged, `main.rs:17`) | no |
| 4 | `not_prepared` | Resolve failed (unresolved variable, cycle, missing secret, keychain secret without `--keychain`, keychain store failed), or auth needs interactive authorization | no |
| 5 | `transport_failed` | Engine failure and `delivery` is `not_sent` or `responded` (see below) | not sent, or responded and then broke |
| 6 | `outcome_unknown` | Engine failure and `delivery` is `unknown` | maybe |
| 7 | `status_unexpected` | Response received; status not acceptable | yes |
| 8 | `output_failed` | Writing the result failed (not a broken pipe) | as reported before the failure |

Precedence when several apply: 4, then 5/6, then 7, then 1. A response with a bad status and failed assertions exits 7; the JSON lists both. *Why 8 instead of the existing `EXIT_IO = 1` (`main.rs:18`):* for `run`, 1 must mean only "an assertion failed", or a CI script cannot trust it. Other commands keep 1.

**Status acceptable:** the status is in `expected_status` when the request declares it (feature 4); otherwise it is below 400 (the rule of `curl --fail`). Redirects are followed per the request's settings before the check.

### Delivery and `outcome_unknown` (E4)

`delivery` is `not_sent`, `unknown` or `responded`. `wisp_service::outcome::delivery` derives it from the terminal event, whether a `Headers` event arrived, and the engine's `nothing_sent` flag. `not_sent` means no byte of this request could have been written to any connection: not the request line, the headers or the body, on any hop or any resend. When that cannot be proved, the value is `unknown`.

**Where the fact is computed.** The engine computes `nothing_sent`, because only the engine sees hops and `reqwest::Error::is_connect()`. Two rules make that possible:

1. While `follow_redirects` is on, the engine follows every redirect itself. `perform` always uses the client with `Policy::none`. The engine already applies reqwest's method rules (`engine.rs:956-1012`), so every request goes through the single `rb.send()` (`engine.rs:909-913`), which is the one counting point. Any future resend path must go through it.
2. A small per-send state, owned by the `Command::Send` task and passed to `perform` by reference, records whether a send started and whether it ended in a connect error. It is set just before each `rb.send()` and read after the `select!`, so it survives a cancel. `nothing_sent` is true only when (a) no send started, or (b) exactly one send started and it failed with `is_connect()` and no response head arrived. Otherwise it is false. The error kind's text plays no part, because `kind_of` matches "tls" and "dns" substrings (`engine.rs:1087-1100`), and a TLS close error after the bytes were written can therefore come out as `Tls`.
3. Every client the engine builds (`client.rs:55-75`) sets `.retry(reqwest::retry::never())`, so reqwest never resends internally and one `rb.send()` is at most one request on the wire. (GUESS: the builder method name and path in reqwest 0.13.5; the task confirms them in `src/retry.rs`.) Without this rule `nothing_sent` and `run`'s no-retry promise are not sound.

**Bytes that leave before the main request.** The OAuth2 token request (`engine.rs:734-744`) and DNS queries are separate requests, not this one, so they do not count: an `Auth` failure from the token fetch is `not_sent`. For HTTPS through a proxy, a failed CONNECT tunnel is a connect error, and only the host and port went to the proxy, so it is `not_sent`. Through a plain-HTTP proxy, the whole request goes to the proxy: a connect failure to the proxy is `not_sent`, a proxy that accepts the request and then fails is `unknown`, and a proxy 502 is `responded`.

| Terminal | `Headers` seen | `nothing_sent` | `delivery` |
|---|---|---|---|
| Completed | yes | — | `responded` |
| Failed, any kind | yes | — | `responded` |
| Failed, any kind | no | true | `not_sent` |
| Failed, any kind | no | false or missing | `unknown` |
| Cancelled | yes / no | — | `responded` / `unknown` |

Every pre-send failure is therefore `not_sent`: a bad URL, Digest with a File body, an unreadable body file, SigV4 signing, and the OAuth2 token. So are connect, DNS and TLS-handshake failures on the first send.

`retry_safe = delivery == not_sent || original method ∈ {GET, HEAD, OPTIONS, PUT, DELETE}`. It uses the method the user sent, not a later hop's method: a POST that a 303 turned into a GET was still delivered. `run` never retries.

**Event change.** `Event::Failed` gains `nothing_sent: bool` with `#[serde(default)]`. A missing value reads as `false`, which is `unknown`, so it fails closed. It is additive. Every match in `app` and the tests uses `..` (`workspace.rs:2797,2806,2887,2945`). The only constructors are `engine.rs:266` and the serde round-trip test (`tests/engine.rs:429`). Nothing outside `core` deserializes `Event`, and history keeps `Outcome::Failed { kind }` unchanged.

**Behaviour change from engine-followed redirects (user decision 2026-11-17, all methods).** Requests that reqwest used to follow (no auth, no Cookie header, only allow-listed headers) now go through the engine:

- at most 9 hops (`engine.rs:977`), with no loop detection beyond that limit;
- an in-memory body is held once more while following (`Replay::Bytes`, `engine.rs:795`).

Methods, headers and cookies on each hop are unchanged (tests `engine.rs:1208,1102`, `cookies.rs:460`).

**Tests** (core, against wiremock or a raw `TcpListener`):

- POST, 307 to a closed port → `nothing_sent=false` → `unknown`, `retry_safe` false.
- POST with Digest: a 401 challenge with `Connection: close`, then the listener is dropped so the retry is refused → `unknown`, `retry_safe` false.
- POST, 303 to a closed port → the hop is a GET, `unknown`, `retry_safe` false.
- POST to a closed port with no redirect → `not_sent`, `retry_safe` true.
- A server that reads the request and then resets the TLS connection → not `not_sent`.
- An HTTP/2 server that answers a POST with REFUSED_STREAM (a protocol NACK) sees exactly one request: the test counts the streams opened, and the result is not a silent retry.
- An unreachable OAuth2 token endpoint → `Auth`, `not_sent`.
- An unreadable body file → `BodyFile`, `not_sent`.
- The serde round-trip with the new field, and an old JSON `Failed` without the field → `nothing_sent=false`.
- Service: the `delivery` table as a pure test, and Cancelled with no headers → `unknown`.

GUESS, for the task to confirm in dependency sources:

- `is_connect()` is true for proxy CONNECT failures and for DNS failures from `TimedResolver`.
- hyper retries a pooled request only when none of it was written.
- rustls 0-RTT early data is off.
- reqwest's default policy allows 10 hops and detects loops.
- Every OAuth2 token-fetch error happens before the main request's first send.

**History vocabulary.** `HistoryEntry` and `NewEntry` (`crates/storage/src/history.rs:303-345`) gain `delivery: Option<Delivery>` (`not_sent`, `unknown`, `responded`; `serde(default, skip_serializing_if = "Option::is_none")`), written by the GUI and by `run --history`. *Why a field and not a new `Outcome` variant:* a 0.3.0 reader drops any index line it cannot parse (`history.rs:1116-1119`), so a new variant would silently hide 0.4.0 entries from 0.3.0. The GUI history list shows "outcome unknown" for `unknown` entries in the existing chip text (`crates/app/src/ui/history.rs`, about 5 lines).

### Implementation

- `crates/service/src/run.rs`: `run_once` opens the collection, scope, request and environment (read-only storage calls as `explain` uses them, `crates/cli/src/cmd/explain.rs:93`), starts an `Engine` with `worker_threads: 1`, `MemoryOnly` refresh tokens (`crates/core/src/auth/oauth2.rs:69`), a fresh `CookieJars`, the default timeout; calls `plan::prepare` with a recording `DynamicSource` (feature 3), `send::submit`, then `recv_blocking` on the event receiver until the terminal event; reads at most `BODY_CAP + 1` bytes of the body (as `workspace.rs:2864`), releases the handle, calls `outcome::finish`, and with `--history` calls `history::record`. The CLI never names `Engine`, `tokio`, `reqwest` or `keychain::`, so `check-boundaries.sh:23-26` keeps its deny-list for `crates/cli/src` unchanged.
- Response bodies over 10 MiB spill to the owner-only temp dir (`crates/core/src/body.rs:14,162`), the exception `docs/architecture.md:231-233` already allows; `run_once` releases the handle before returning. A killed process can leave one spill file (same as a GUI crash).
- `crates/cli/src/cmd/run.rs` maps `RunReport` to `RunDoc` in `dto.rs` and picks the exit code. `main.rs` gains the `Run` arm.

### Security and redaction

- No secret value in stdout, stderr or the history entry. Canary test extended from 0.3.0 (0.3.0 spec feature 4, rule 8): file secret used in URL path, query, header and auth; a plain variable named `api_token`; a keychain env with `--keychain` against a `MemoryStore` test seam (never the real keychain); the response echoes every canary in headers and body; assert no canary in stdout, stderr, `index.jsonl` or `<id>.req.json`, in both formats and for exit codes 0, 1, 4, 5, 6, 7.
- Read-only test extended: `run` without `--history` leaves the collection tree, mtimes and a temp data dir (`WISP_DATA_DIR`) unchanged and the spill dir empty; with `--history` the only new files are under `history/<id>/` in the data dir.
- No `tracing` subscriber (unchanged).

### Tests

Against a local mock server (the `wiremock` setup in `crates/core/tests/engine.rs`): one test per exit code 0, 1, 4, 5, 6, 7 (6 via a server that accepts and never answers, with a short request timeout); the delivery tests listed under E4 (core) and the `delivery` table as a pure test (service); `expected_status` absent with 404 exits 7; precedence (bad status plus failed assertion exits 7); argument-parser table extended; JSON golden with schema check.

## Feature 3 — Dynamic values once per send (E3)

### Behaviour

- `{{$uuid}}` and `{{$timestamp}}` are generated once, when a send is prepared, and never again for that send. The engine never re-resolves (a Digest retry resends the prepared bytes, `engine.rs:584`).
- `run` reports every generated value (name and value, in order of use). Dynamic values are not secrets.
- The URL bar's live problem check (`crates/app/src/ui/url_bar.rs:408`) resolves per keystroke and today generates a fresh UUID each time; it switches to a placeholder source, so previews are deterministic and generate nothing.
- Explain already never generates (`crates/core/src/resolve/report.rs:1063`); unchanged.
- Each occurrence still gets its own value, as today (`resolve/engine.rs:284-291`); user decision 2026-11-17.

### Data model and implementation (`core`)

- `crates/core/src/resolve/engine.rs`: a `DynamicSource` trait (`fn generate(&mut self, name: &str) -> Option<String>` for `uuid` and `timestamp`), with `Fresh` (today's code), `Recording` (wraps `Fresh`, keeps `Vec<DynamicValue>`) and `Placeholder` (fixed `00000000-0000-4000-8000-000000000000` and `0`). `Resolver` holds `&mut dyn DynamicSource`. New `pub fn resolve_with(req, scope, &mut dyn DynamicSource)`; `resolve()` keeps its signature and uses `Fresh`, so its 764 lines of tests (`resolve/tests.rs`) are untouched.
- `DynamicValue { name, value }` re-exported from `resolve/mod.rs`. No change to `PreparedRequest`.

### Tests

`resolve_with` + `Placeholder` is byte-identical across calls; `Recording` lists one entry per occurrence in order; the GUI send records the same values that went on the wire (mock server echoes the header).

### Size estimate

+1 to 3 KB.

## Feature 4 — Request metadata (D3)

### File format (additive, `format = 1` unchanged)

```toml
name = "Create order"
method = "POST"
url = "{{base}}/orders"
description = """
Creates an order. Idempotency key required in production.
"""
expected_status = 201          # or a list: expected_status = [200, 204]
```

- `description`: a TOML string, any length on disk; shown up to 1,000 characters (Explain, CLI `explain`, `snapshot`), cut with "…". `inspect` shows only whether one exists.
- `expected_status`: an integer 100-599, or an array of 1 to 16 such integers. Anything else is an invalid-key error naming `expected_status`, as `settings.timeout_ms` is today (`crates/storage/src/request.rs:129-138`), and `validate` reports it.
- Both are top-level keys, written only when non-empty or already present (the keep-what-exists rule `write_request` applies to `[auth]`, `request.rs:571,592`). 0.3.0 ignores unknown top-level keys on load and keeps them on save, because `write_request` edits the document in place (`request.rs:569-600`); a fixture test proves it as 0.3.0 did for `[[assert]]`.
- `expected_status` is not an assertion: it decides exit 7, while a `[[assert]] kind = "status"` decides exit 1. Both may exist.

### Data model

- `Request` (`crates/core/src/request.rs:310-323`) gains `description: String` and `expected_status: Vec<u16>`, both `serde(default)`; `Default` (`:325-340`) sets them empty. `requests_equal` (`storage/src/request.rs:353`) compares them, so an outside edit to either raises the disk-change banner like any other key.
- Literal sites to update: `storage/src/import/curl.rs:616`, `import/openapi.rs:504`, `import/mod.rs:108`, `storage/src/request.rs:106` and its tests (`:1328-1771`). Mechanical.
- `ResolutionReport` (`resolve/report.rs`) gains `description` (capped, typed `Shown::Text`) and `expected_status`, so the GUI pane and CLI `explain` read the same thing. CLI `ExplainDoc` and `NodeInfo` (`dto.rs:44,76`) gain `description` / `has_description` and `expected_status` (additive under `wisp-cli/1`).
- History's stored request copy keeps both (authored, non-secret metadata).
- Importers: Postman and OpenAPI descriptions land in `description` (OpenAPI reads it today for servers, `import/openapi.rs:370`). Done in the H4 task, which owns those files; user decision 2026-11-17.

### Security

A description is authored text in a committed file, like a request name: it is printed, capped, and never masked. It is not expanded: a `{{var}}` in it stays literal, so no secret can reach it through resolution.

### Size estimate

Core and storage +3 to 6 KB; Explain display +3 to 6 KB.

## Feature 5 — `wisp-cli snapshot` (C3)

### Command and shape

```
wisp-cli snapshot <collection> [--env <name>] [--request <request-path>] [--recent <n>] [--json]
```

One document from persisted files only, built from the existing DTOs:

```json
{"schema":"wisp-cli/1","command":"snapshot","wisp_cli":"0.4.0",
 "source":"persisted files only; unsaved edits in the app are not included",
 "collection":{...CollectionInfo},
 "environments":[...as inspect],
 "tree":[...NodeInfo], "tree_truncated":false,
 "validation":{"errors":0,"warnings":2,"findings":[...FindingInfo],"findings_truncated":false},
 "request":{...ExplainDoc} ,
 "recent":[{"at":1763380000000,"request":"orders/create.toml","method":"POST",
            "url":"https://api.example.com/orders","outcome":"completed","delivery":"responded",
            "status":201,"environment":"staging",
            "assertions":[{"label":"status equals","state":"pass"}]}],
 "truncated":[]}
```

- `request` only with `--request`; `recent` only with `--recent n`, n from 1 to 50 (default none).
- **Bounds:** tree 2,000 nodes (as `inspect`); findings 500; `recent` 50; environments listed at most 200; variable names per environment at most 500; the `request` ExplainDoc at most 500 variables and 500 headers; names 200 characters; descriptions 1,000. The serialised document is at most 1 MiB, enforced by dropping, in order: `recent`, `findings`, `tree` entries from the end, then the `request` detail (replaced by `{"omitted":true}`), then each environment's variable list (the count is kept). Each drop is named in `truncated`. No timestamp of the snapshot itself, so two snapshots of an unchanged collection are byte-identical.
- **Final fallback:** if the document is still over 1 MiB, emit only `schema`, `command`, `wisp_cli`, `source`, the collection info, a count per section, and `truncated` naming every dropped section. Exit 0, with a note on stderr. This minimal form is small by construction, because names are capped at 200 characters.
- `recent` uses a new read-only API, `HistoryStore::open_read_only(dir) -> Option<ReadOnlyHistory>` with `list(limit)`, in `crates/storage/src/history.rs`. It never migrates, never takes the lock, and never creates, renames or writes any file. (`HistoryStore::open` migrates legacy history, creates lock and marker files and can rewrite stored data, so `snapshot` must not use it.)
- If the store has no current scrub marker (legacy or unmigrated), `recent` is empty with the note "history not yet migrated; open Wisp once". It does not read data that might be unscrubbed.
- The rest of the `recent` path is unchanged: `DataDir::resolve()` (`crates/storage/src/data_dir.rs:52`, computes a path, creates nothing) and `read_collection_id`. No id or no index: `recent` is empty with a note. History URLs print origin and path without query, as `inspect` does.
- Text output: the same sections as `inspect`, `validate` and `explain`, under headings.

### Security and read-only

All 0.3.0 CLI rules hold (DTOs only, secrets replaced by placeholders before scope building, no keychain, no writes). `snapshot` never takes `--keychain`. Canary and read-only tests from 0.3.0 run against `snapshot` in both formats, with a history fixture whose index holds canary strings in fields the DTO does not map.

### Tests

A synthetic collection built to exceed every cap gives output of 1 MiB or less, with `truncated` listing the sections dropped; the final fallback is covered by a fixture that stays over 1 MiB after every other drop.

Snapshot history: (a) a history dir without the scrub marker gives an empty `recent` with the note "history not yet migrated; open Wisp once", and the dir listing, sizes and mtimes are identical before and after; (b) a migrated store lists its entries, and nothing in the dir changes.

### Size estimate

CLI only, +20 to 40 KB (GUESS).

## Per-user and security invariants (all features)

- No secret value in a `run` result, a `snapshot`, an `explain`, a history entry or stored request copy, a log line or a panic message. One canary test per surface.
- `run` writes only: history under the per-user data dir with `--history`, and body-store spill files it removes. It never writes the collection, `settings.toml`, cookie files or a collection id.
- `snapshot`, `inspect`, `explain` and `validate` write nothing.
- `run` opens the OS keychain only with `--keychain`. Tests use `MemoryStore`/`NoStores` (`storage/src/vault.rs:100-125`); no test touches the real keychain.
- `run` never retries. `delivery` and `retry_safe` tell the caller what is safe.
- The GUI's history redaction (`docs/architecture.md:234-237`) is unchanged; `delivery` is not sensitive.

## Risks

1. **CLI size.** The network stack may push Linux past 4 MiB. Mitigation: 2M measures right after 2A; the raise is pre-approved (user decisions).
2. **Extraction regressions.** C1 moves the send and history path of a 6,427-line file. Mitigation: two serial tasks, the golden `NewEntry` test built before the move, no behaviour change allowed in wave 1.
3. **`outcome_unknown` misclassification.** `ErrorKind` is coarse (`Other` covers SigV4 signing and Digest parse failures before any byte is sent, `engine.rs:891,931`). Mitigation: Resolved by the engine-computed `nothing_sent` (E4); pre-send SigV4 and Digest errors are `not_sent`.
4. **Keychain prompts on macOS for `wisp-cli`.** Per-binary ACLs may prompt on first `--keychain` use (GUESS). Mitigation: hand test in 3M; docs say so. Opt-in by D-F, so CI without `--keychain` never sees it.
5. **History written by two processes.** GUI and `run --history` append to the same store. Appends take a process mutex and a file lock (`storage/src/history.rs:896-897`, `lock_file` `:993-1020`), so a second process is serialised. 2A adds a two-process append test to prove it.
6. **Spill files on kill.** A killed `run` with a >10 MiB body can leave one spill file in the private temp dir. Documented.
7. **Stale AC line numbers.** Task 99 cites 0.2.0 lines. The table above corrects the ones checked; implementers re-locate the rest.
