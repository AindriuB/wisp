# Wisp 0.2.0 — design spec

Status: agreed 2026-11-09 in a shaping session, from the architect's design plus the user decisions below. Architectural work; hand to `/plan`. Builds on the v1 spec, `2026-10-29-http-client-v1.md`, whose "Not in v1" list this release works through.

## Outcome

Wisp 0.2.0 closes the largest gaps between Wisp and the clients it replaces, without losing the reason it exists. A developer can bring existing work in (curl, Postman, OpenAPI), call APIs that need OAuth2, Digest or AWS SigV4, see where a request's time went, look back at what was sent, keep secrets in the OS keychain if they choose, and keep several collections open at once.

**Success:** all of the above work on macOS, Windows and Linux, and the Windows release binary stays at or under 15.5 MB (measured; the budget is 16 MiB = 16.78 MB).

## User decisions (2026-11-09)

- **Scope:** importers (curl, Postman v2.1, OpenAPI 3 JSON and YAML); request history; OAuth2 (client credentials, and auth code with PKCE via the system browser and a loopback redirect), Digest and AWS SigV4; optional per-environment OS keychain secrets; multiple collections open at once; phase timings and a persisted cookie jar.
- **History** lives in the per-user data dir, never in the collection. Auth values are redacted and never stored; resend re-resolves against the current environment and says so. Bodies are stored, capped at 1 MiB per entry. Defaults are 500 entries per collection, failed requests kept, and a Clear history action.
- **Keychain** is optional per environment; secrets files stay the default. The collection ID is a random ID written once into `collection.toml`, so secrets survive moving the folder. When the keychain is unavailable (portable mode, headless Linux), fall back to the file with a visible banner.
- **OAuth2 refresh tokens** are persisted only for keychain-backed environments; otherwise they are memory only.
- **Timings** are DNS / Connect+TLS (combined) / First byte, plus total. No TCP/TLS split. Reused connections report no connect phase.
- **Cookie jar** persistence is off by default, with a per-collection toggle.
- **Importers:** OpenAPI `servers` become environments. Postman scripts are skipped with a warning.
- **Architecture rule:** "writes nothing outside the collection folder and settings.toml" becomes "... plus the per-user data dir (history, cookies)".
- **Dependencies:** hand-roll Digest, SigV4, OAuth2 and PKCE on `sha2`/`hmac`/`md-5`. Use `saphyr` (or `yaml-rust2`) for YAML, never `serde_yaml`. The Linux keychain gets a spike first: if `zbus` costs more than 1 MB, Linux keychain ships as unsupported (fallback to the file) in 0.2.0.

## Shape

No new crate. Importers, history and keychain live in `storage`; auth, timings and the cookie jar live in `core`; multiple collections and all new UI live in `app`. `core` stays free of GPUI and `storage` stays free of `core`-internal runtime types. `resolve()` stays pure: schemes that need I/O or the final request bytes are applied in the Engine.

## Per-user data dir

New in `storage`, and the base for history and cookies. Location: the OS data dir, or `<exe-dir>/data` when the `portable` marker exists (the same rule as `settings.toml`). Directories are 0700 and files 0600; reuse `atomic_write_private` from the environment code. If the dir is unwritable, the features that need it are disabled with a banner and nothing else fails. Each collection is addressed in it by its random collection ID (see Keychain), not by a path hash.

This lands first in wave 1; history and cookies build on it.

## Per-feature design

### 1. Importers (`storage::import::{curl, postman, openapi}`)

Pure functions returning one `ImportResult` (requests, folders, warnings), written through the existing `ops`/`save_request` path. Collection `format = 1` is unchanged. `app` gets a command-bar entry and an "Import..." dialog.

- **curl:** hand-written parser (about 300 lines): quoting, `-H`, `-d`, `-X`, `-u`, `--data-*`, `-F`, `-b`, `-k`, `-L`.
- **Postman v2.1:** `serde_json`. `:name` path params convert to `{name}`. Variables become collection vars. Scripts and pre-request scripts are skipped with a warning. Postman auth secrets go to a `*.secrets.toml`, never a committed file.
- **OpenAPI 3:** JSON via `serde_json`, YAML via `saphyr`. `{name}` path syntax converts directly. `servers` become environments. Examples are used for bodies where present.
- **Failures:** unsupported constructs (scripts, GraphQL, multi-file `$ref`) become entries in a warnings report shown to the user, never silent drops. Name collisions are suffixed. Input size and nesting depth are capped against hostile files.

### 2. History (`storage`)

Replaces the existing per-collection `.wisp/history.jsonl` (metadata only, 1 KiB preview, 4 MiB rotation), which is ignored and left alone.

- **Layout:** `history/<collection-id>/index.jsonl` (one metadata line per send, including phase timings once wave 2 lands), plus `bodies/<id>.bin` for the response and `<id>.req.json` for the request.
- **Redaction:** the stored request keeps the unresolved form of auth (variable references only) and no auth values; headers that carry credentials are redacted. Resend re-resolves against the current environment and the UI says so. This supersedes the architect's recommendation of exact resend.
- **Caps:** 500 entries per collection (evict oldest first), 1 MiB per body (larger bodies truncated and marked), and a total bytes cap. Failed requests are kept.
- **Controls:** a Clear history action, and settings toggles for "do not store response bodies".
- **UI:** a history panel; reopening an entry shows the stored response read-only through a file-backed `BodyHandle`; Resend.
- **Failures:** a corrupt line is skipped (torn-line recovery exists in `history.rs`); disk full drops the entry and shows a banner; an unwritable data dir disables history.
- `core` is unchanged: resend is a re-resolved `PreparedRequest` through `Command::Send`.

### 3. Auth (`core`)

New `Auth` variants: `Digest`, `OAuth2ClientCredentials`, `OAuth2AuthCode` (with PKCE) and `AwsSigV4`. Each has a hand-written redacting `Debug` and a `debug_redacts_*` test (`docs/conventions.md`). TOML form is `[auth] type = "digest"` and so on, through the codec; values are normally `{{vars}}` so secrets stay in the secrets file. The auth editor in `app` gains the new types.

- **Digest:** the Engine sends, reads `WWW-Authenticate` from the 401, and retries once. Algorithms MD5, SHA-256 and SHA-512/256; tested against RFC 7616 vectors. The body must be replayable: File and streamed bodies fail with a clear error rather than being buffered.
- **AWS SigV4:** applied in the Engine just before send, over a hash of the body; streamed File bodies use `UNSIGNED-PAYLOAD`. Tested against the AWS test suite.
- **OAuth2 client credentials:** the Engine fetches the token, caching in memory by (token_url, client_id, scope) with expiry. Access tokens are never written to disk.
- **OAuth2 auth code + PKCE:** new `Command::AuthorizeStart{..}` and `AuthorizeCancel`, and events `AuthUrl{url}` (the app opens the system browser), `AuthCompleted` and `AuthFailed`. The Engine binds a loopback listener on 127.0.0.1 with an ephemeral port, validates `state`, exchanges the code, and times out after 120 s by default.
- **Refresh tokens** are persisted (keychain) only for keychain-backed environments; otherwise memory only.
- **Failures:** browser cannot open (show the URL for copy), listener port unavailable, `state` mismatch, token endpoint errors (body shown, redacted).

### 4. Keychain (`storage`)

A `SecretStore` trait with two implementations: the file store (default, current behaviour) and the OS keychain via `keyring`. Per environment, `environments/<env>.toml` gets `secrets = "keychain"` (default `"file"`); the line is committed and harmless.

- **Collection ID:** a random ID written once into `collection.toml` (a committed file; the field is additive and `format` stays 1). Entries live under service `wisp`, account `<collection-id>/<env>/<var>`, so moving or renaming the folder keeps secrets. A collection without an ID gets one on first open that writes.
- **Fallback:** the keychain is probed at runtime. If unavailable (the `portable` marker is present, or headless Linux without Secret Service), the environment falls back to the secrets file with a visible banner, and the option is disabled in the UI. Values already in the keychain are never silently copied to plaintext, and the load never fails.
- **Switching modes** is an explicit migrate action: move the values, then delete the old file or entries.
- **Failures:** a denied or locked keychain prompt leaves the variables unresolved and Send is blocked by the existing unresolved-variable message. Values are never logged.
- **Linux:** a spike comes first. If `zbus` costs more than 1 MB, Linux keychain ships as unsupported (fallback to the file) in 0.2.0. `dbus`/libdbus is rejected: it breaks the self-contained-binary rule.
- `core` is unchanged; `Scope` already takes resolved environment variables.

### 5. Multiple collections (`app`)

`Workspace` (`crates/app/src/workspace.rs`, the hottest file) becomes a list of open collections, each with its own tree, watcher, environment selection and tabs. The Engine and its client cache stay shared; the cookie jar is keyed per collection. `settings.toml` stores the open list and the last active one.

- **Failures:** a missing path at startup is dropped with a notice; opening an already-open folder focuses the existing one.
- **Memory:** each watcher and tree costs RSS; cap the open count (about 8) and measure.

### 6. Phase timings (`core`)

Reported phases are DNS / Connect+TLS / First byte, plus total. Reqwest exposes a resolver hook (`dns_resolver`) for exact DNS time and a `connector_layer` that wraps the whole connect service, giving connect+TLS as one number. A TCP/TLS split would mean replacing reqwest's connector with hyper-util and hyper-rustls and re-implementing proxy, redirects, decompression and cookies, so it is out.

- Reused (pooled) connections never call the connector, so their connect phase is `None`, not zero. Under pooling a connection set up for request A may serve request B; B reports no connect phase.
- Clients are shared across requests, so timings are attributed to a `RequestId` through a per-connection slot that the response path drains.
- First byte already exists as `Event::Headers.ttfb`.
- A one-day spike confirms the attribution is race-free under pooling and HTTP/2 before the feature is built. The spike result decides the wiring; if attribution cannot be made race-free, ship DNS and total only and record why.
- Timings are carried on `Completed` and stored with history entries.

### 7. Cookie jar (`core`)

Turn on reqwest's `cookies` feature and set `cookie_provider` to a Wisp store, which makes the jar per collection and persistable. The jar handle is passed in `EngineConfig` (preferred over a `Command::ClearCookies`).

- **Persistence is off by default**, with a per-collection toggle. When on, the file is `cookies/<collection-id>.json` in the per-user data dir (0600), written debounced and on exit; session cookies are dropped and expired ones pruned. Cookies hold session secrets and get the same protections as history.
- **UI:** a Cookies manager (list, delete, clear) alongside the toggle. The existing response-side `Set-Cookie` display in `app/src/cookies.rs` is separate and unchanged.
- The engine's client build is touched here and by timings, so those two are serialised.

## Dependencies and size estimates

All figures are Windows release-binary estimates from the architect's source reading, not measurements. Each is confirmed by the wave's measure run.

| Need | Choice | Estimate | Notes |
|---|---|---|---|
| YAML | `saphyr` (or `yaml-rust2`) | +60-120 KB | Not `serde_yaml` (archived). Hand-rolled subset parser rejected: anchors and multiline scalars. Spike. |
| SigV4 | hand-rolled on `sha2` + `hmac` | +10-20 KB | About 150 lines. `aws-sigv4` is far larger. Already in the lock via `app`. |
| Digest | hand-rolled on `md-5` + `sha2` | +5-10 KB | About 150 lines. |
| OAuth2 + PKCE | hand-rolled over reqwest, `serde_json`, tokio `net`, `sha2`, `base64` | +15-30 KB | No `oauth2` crate. Verifier from `getrandom` (check it is in `core`'s tree). |
| Keychain | `keyring` with per-platform features | Windows +30-80 KB; Linux unknown | Linux Secret Service via pure-Rust `zbus` is the largest risk (guess 0.5-1 MB). Spike first. |
| Cookies | reqwest `cookies` feature | +80-150 KB | Pulls `cookie_store` and `cookie`. Spike. |

Combined estimate: Windows +0.3 to 0.6 MB against about 2.3 MB of headroom (13.7 MB measured against the 16 MiB budget, 16.78 MB). Linux has about 4.0 MB of headroom (24.0 MB measured against 28 MiB, 29.36 MB). RSS is expected to grow only with open collections and the OAuth token cache; history and cookies are on disk. The after-one-request budget is 128 MiB and Windows measured about 50 MB private.

Hand-rolling security-sensitive code saves roughly 0.5 MB and costs a surface we must test: RFC 7616, AWS SigV4 and RFC 7636 (PKCE) vectors are mandatory tests, not optional ones.

## Timing and other limits

- OAuth2 auth-code wait: 120 s default, cancellable.
- Digest: one retry only.
- History: 500 entries per collection, 1 MiB per body, a total bytes cap.
- Open collections: about 8.
- Import input: capped in size and nesting depth.
- Timing spikes (phase attribution, Linux keychain) are time-boxed to about one day each.

## Waves

Any work in `workspace.rs` is serial within and across waves.

**Wave 1 — foundations.**
- (a) Per-user data dir with the portable rule in `storage`, then the history rewrite on top of it.
- (b) Importers: new `storage::import` module in separate files, plus the Import dialog in `app`.
- (c) Auth Digest and SigV4 in one task (core `auth` module and codec arms; `request.rs` and `codec.rs` are shared files).
- Importers and history are parallel-safe once the data-dir helper lands. Sequence the history UI after the importers' UI, or give each its own module, because both touch `workspace.rs`.

**Wave 2 — needs wave 1.**
- OAuth2 client credentials and auth code + PKCE (reuse the auth variants, codec and Engine command surface).
- Cookie jar (reuses the data dir).
- Phase timings (after history, so entries carry timings).
- The cookie jar and timings both touch the engine's client build, so they are serial.

**Wave 3 — risky and UI-heavy.**
- Multiple collections (a heavy `workspace.rs` rewrite; alone or last).
- Keychain (needs the collection ID and the Linux spike). The collection ID change to `collection.toml` can land earlier if history or cookies need it; history and cookies key on it from wave 1, so it ships with the data dir.

## Size gate

Each wave ends with a measure run (`scripts/measure/measure.sh`, with the CI baseline for Windows). The wave fails, and its merge is held, if the Windows release binary exceeds 15.5 MB. The Linux and macOS figures are recorded too and must stay within their existing budgets in `docs/architecture.md`. A failed gate is resolved by dropping or replacing the dependency that caused it, not by raising the budget.

## Not in 0.2.0

A TCP/TLS timing split; scripting; GraphQL; global variables; a CLI runner; persisting access tokens; Postman script translation; code signing for Windows and Linux.

## Notes for the planner

- Open question carried from the design: whether `getrandom`, tokio `net` and `windows-sys` are already in `core`'s tree is unchecked; the wave 2 task checks it.
- Not read by the architect: `app` UI code beyond `workspace.rs`, the codec internals, the watcher and the `ops` API. File-ownership claims in Waves come from line counts and module names; each task file must confirm them.
