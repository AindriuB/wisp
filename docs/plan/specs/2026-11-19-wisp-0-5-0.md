# Wisp 0.5.0 — design spec

Status: AGREED 2026-11-19; the user accepted all eight recommendations ("Accept, fan out"), recorded under Decisions at the end. Scope is the roadmap's 0.5.0 section (`docs/plan/roadmap.md:163-174`), decisions D-H, D-K, D-1, D-I and D-G (`roadmap.md:198-216`), plus private CA trust, which the user added on 2026-11-19. This spec does not reopen those decisions. Inputs: the roadmap, the 0.4.0 spec (`docs/plan/specs/2026-11-17-wisp-0-4-0.md`), task 99's hardening ACs (`docs/plan/tasks/99-hardening-0-2-0.md`) and the 0.4.0 follow-ups in `docs/plan/PLAN.md:27-150`. Citations are `path:line` at `e22eae6` (0.4.0 released). Guesses are marked GUESS.

## Outcome

Wisp 0.5.0 can compare two runs of a request: status, headers and a structural JSON body diff. Volatile fields the user chooses to ignore are left out. When a body was not stored, or was cut short, the diff says so instead of reporting the sides as equal. A request can have a GraphQL body (query plus variables), and it round-trips to TOML. The Postman importer turns a closed set of `pm.test` checks into `[[assert]]` entries and warns about the rest. HTTPS servers signed by a private CA can be verified through the OS trust store or a user-chosen CA file, so `verify_tls = false` is no longer the only workaround. The deferred binding-registry (H3b) and importer (H4b) hardening closes, and so do the scheduled 0.4.0 follow-ups.

**Success:**
- Every compare result states missing or truncated evidence explicitly and applies the user's ignore list (feature 2 tests).
- A GraphQL request round-trips file → model → file unchanged.
- The importer translates the closed set and warns about everything else.
- A request to a server signed by a private test CA fails by default. It succeeds with that CA's file configured, and it succeeds through the OS store on the user's Mac (hand test).
- Every listed H3b and H4b AC is closed.
- The three known flakes are fixed.
- The Windows GUI exe is at or under 16,000,000 B.
- The macOS hand test is done before the tag (D-I).

## User decisions (binding)

- **D-H** Compare is structural JSON plus a status and header diff, with a user ignore list. A text diff is deferred.
- **D-K** GraphQL is a body mode: query plus variables JSON, pretty-printed, with no introspection and no schema explorer. Postman translation covers a narrow closed set only. General scripting is dropped.
- **D-1** The Windows GUI gate is 16,000,000 B and the soft line is 15,900,000 B. The 0.4.0 Windows GUI is 15,616,000 B (`scripts/measure/results/v0.4.0-wave-3-size.json`), which leaves 284,000 B under the soft line.
- **D-I** Release testing is mac-first: tag after the macOS hand test, and the release notes say which platforms were tested.
- **D-G** Agent-write features (C4, C5b, C6) stay deferred.
- **2026-11-19 (user):** "Add CA support to 0.5.0": verify servers whose chain ends at a private CA, through the OS store and/or a user CA bundle, with tests, a size figure and docs. Also add a README carry-over on putting `wisp-cli` on `PATH` on macOS.

## Goals and non-goals

**Goals:** comparison and evidence; the GraphQL body; Postman checks import; private CA trust in both the GUI and `run`; closing H3b and H4b; the scheduled carry-overs. Every file-format and history change is additive: `format = 1` is unchanged.

**Non-goals (later, with reasons):**

| Later | Why not 0.5.0 |
|---|---|
| Text or line diff of non-JSON bodies | D-H. Non-JSON bodies are compared for byte equality only. |
| `wisp-cli compare`, and copy or export of a diff | The audit requires export redaction before a diff leaves the screen (audit §7 "Guardrails"); history redaction alone is not enough. This is a candidate for 0.6.0. |
| Array diff by LCS or keyed matching | Arrays are compared by position. A keyed match needs user configuration. |
| GraphQL over GET, `operationName`, introspection, schema, autocomplete | D-K. A document with several operations can still be sent; the server picks one or rejects it. |
| Client certificates (mTLS) | Not requested. This needs identity storage and keychain work. |
| Collection- or environment-level CA settings | Trust is per user (open question 1). |
| Folder-level or collection-level Postman test scripts, pre-request scripts | They keep the existing warning (`crates/storage/src/import/postman.rs:94-114`). |
| 0.3.0-era 🔒 items in `PLAN.md:190-290` | They are not 0.4.0 carry-overs; the scribe triages them for 0.6.0. |

## Shape

No new crate. Each feature lives where the boundary rules (`docs/architecture.md:222-226`) put it:

- **Trust:** `wisp-core`, in a new `trust.rs` module and in the `ClientCache` (`crates/core/src/client.rs`). The PEM loader is there too, because both binaries need it and `core` already reads files for bodies.
- **Compare:** `wisp-service`, in a new `compare.rs` module. It is pure, takes the storage history types, and needs no GPUI.
- **Ignore list:** stored in `collection.toml`, by `wisp-storage` (`crates/storage/src/collection.rs`).
- **GraphQL:** a new `Body` variant across core, storage, service and app.
- **Postman translation:** `wisp-storage`, in `import/postman/**`.

## Feature 1 — History evidence (completeness flags)

`HistoryEntry` (`crates/storage/src/history.rs:323-362`) has `body_stored` and `body_truncated`, but it cannot tell why a body is missing. Today the GUI pre-filters the body by the setting (`crates/app/src/workspace.rs:2729`, `ui/history.rs:26`) and then passes `HistoryBodies::Store`. `run` passes `Skip` (`crates/service/src/run.rs:599`).

**Additive field** `evidence: Option<Evidence>` (serde default, skipped when `None`):

| Field | Values | Meaning |
|---|---|---|
| `body` | `stored` | The whole response body is in the store. |
| | `truncated` | Only the first `BODY_CAP` bytes are stored. |
| | `off` | The caller chose not to store bodies (the GUI setting is off, or the entry came from `wisp-cli run`). |
| | `unreadable` | The response completed, but its body could not be read for the store. |
| | `no_response` | The outcome was Failed or Cancelled before a body existed. |
| `headers` | bool | True when the entry carries the response head (`status` is `Some`). |

`None` means the entry was written before 0.5.0: compare falls back to `body_stored` and `body_truncated` and says "recorded before 0.5.0". `body_stored` and `body_truncated` are still written as today. The GUI passes the setting to `record` instead of pre-filtering, so `off` and `unreadable` are told apart.

## Feature 2 — Response compare (D2b)

### Behaviour

From the History panel the user can do two things:

- compare an entry with the previous entry of the same request path, in one click;
- mark one entry, then choose another one from the same collection's history.

The compare view shows:

1. **Provenance, for each side:** time, request path, method and URL template, environment name, outcome or status, the delivery chip and the checks chip.
2. **Status:** equal, changed, or missing on one side.
3. **Headers.** Names are compared case-insensitively. Repeated headers are compared as ordered value lists. A header whose value history emptied is reported as "redacted" and its values are not compared.
4. **Body.** Both bodies must be stored complete and both must parse as JSON. Then the view lists changes as RFC 6901 JSON Pointer paths: added, removed, changed, or type changed.
   - Arrays are compared by position.
   - Integers are compared exactly; if either side is a float, both are compared as f64.
   - If either side is not JSON, the view reports byte equality and "text diff not available".
   - If either side is incomplete, it reports the evidence reason for each side and never says "equal".
5. **A count of the differences the ignore list hid.**

**Evidence wording:**

| Evidence | Text |
|---|---|
| `off` | body not stored (history bodies off, or a `wisp-cli run` entry) |
| `unreadable` | body could not be read when recorded |
| `no_response` | no response body (request failed or was cancelled) |
| `truncated` | body cut at 1 MiB; not compared |
| `None` | recorded before 0.5.0 |

### Ignore list

- **Where it lives:** `collection.toml`, with the user's answer to open question 4 deciding:

  ```toml
  [compare]
  ignore = ["header:date", "body:/meta/requestId", "body:/items/*/updatedAt"]
  ```

- **Syntax:**
  - `header:<name>` matches a header name, case-insensitively.
  - `body:<pointer>` is an RFC 6901 pointer. A `*` segment matches any one key or index. A pattern also ignores everything below the path it names.
- **Limits:** at most 256 patterns of at most 1,024 bytes each. An invalid pattern is listed with its reason and is never dropped silently.
- **No built-in patterns** (open question 5).
- **Adding a pattern:** each change row has "Ignore". It shows the exact pattern and says it will be written to `collection.toml`, which may be shared through git. After confirmation it appends the pattern. The ignore list is shown in the view with a remove action.
- **Writing:** storage uses `toml_edit` in place under the existing root lock (`crates/storage/src/collection.rs:177-201`), so comments and other tables are kept.

### Model (`crates/service/src/compare.rs`, sketch)

- `IgnoreList::parse(&[String]) -> (IgnoreList, Vec<PatternProblem>)`.
- `compare(a: Side, b: Side, ignore: &IgnoreList) -> Comparison`, where a `Side` is a `HistoryEntry` plus an optional `StoredEntry`.
- `Comparison` holds: a status diff, header changes, a body result (`Json(changes)`, `Equal`, `NotJson { equal }`, `Incomplete { a, b }` or `TooDeep`), the ignored count and the total change count.
- At most 1,000 changes are listed. Values are cut to 256 characters with a flag. JSON depth is capped at 128.
- The comparison is linear in node count.

### Security

- Values come only from stored history, which is the same exposure as opening an entry today.
- There is no copy or export (non-goals).
- Pattern text holds paths and header names, never values.
- Displayed values have control and bidi characters escaped.

### Size estimate

+40 to +60 KB (roadmap), compare engine included.

## Feature 3 — GraphQL body mode

- **Model:** `Body::GraphQl(GraphQlBody { query: String, variables: String })` (`crates/core/src/request.rs:280-290`).
- **File format:**

  ```toml
  [body]
  type = "graphql"
  query = """..."""
  variables = """{ ... }"""
  ```

  When `variables` is absent it is the empty string. Bodies are inline only; there are no sidecar files.
- **Resolve** (`crates/core/src/resolve/engine.rs:675-700`):
  - `{{var}}` is substituted in both fields.
  - The body sent is the compact JSON `{"query": q}`, plus `"variables": <object>` when the substituted variables are not blank.
  - If the variables are not a JSON object after substitution, resolve reports a problem with fixed text and no value.
  - The Content-Type is `application/json` unless the request sets one, as for JSON bodies.
- **Explain:** the `BodyKind` label is `graphql`. The CLI picks it up through `label()` (`crates/cli/src/cmd/explain.rs:285`).
- **History:**
  - The query is redacted like a Text body; the 168 note on whole-text clearing applies, which fails safe.
  - The variables are redacted like a JSON body.
  - Both are capped at `BODY_CAP` with `truncated` set, and the 178 resend refusal applies.
- **Import:** the credential scan covers both fields (`crates/storage/src/import/mod.rs:363`). Postman `mode = "graphql"` is imported (feature 4).
- **Editor:** a GraphQL kind in the body picker with Query and Variables editors, `{{var}}` highlighting, a Format action on the variables, and an inline note when they are invalid.
- **Compatibility:** 0.4.0 cannot read a `graphql` body; it reports the file as invalid. The release notes say so.
- **Size:** +20 to +35 KB.

## Feature 4 — Postman test translation (D-K)

Only request-level `event` scripts with `listen = "test"` are translated. A `pm.test("…", function () { … })` (or an arrow function) is translated only when every statement in it is in this closed set. Otherwise none of it is translated:

| Postman statement | `[[assert]]` |
|---|---|
| `pm.response.to.have.status(<int>)` | status equals `<int>` |
| `pm.expect(pm.response.code).to.eql(<int>)`, `.to.equal(<int>)` | status equals `<int>` |
| `pm.response.to.have.header("<n>")` | header `<n>` exists |
| `pm.response.to.have.header("<n>", "<v>")` | header `<n>` equals `"<v>"` |
| `pm.expect(pm.response.headers.get("<n>")).to.eql("<v>")` | header `<n>` equals `"<v>"` |
| `pm.expect(pm.response.headers.get("<n>")).to.include("<v>")` | header `<n>` contains `"<v>"` |
| `pm.expect(pm.response.json().<a.b[0].c>).to.eql(<literal>)` (open question 7) | json path equals `<literal>` |

Literals are integers, floats, single- or double-quoted strings with simple escapes, `true` and `false`.

**Warnings.** A request with untranslated tests gets one warning: "K of N tests not translated; scripts are not run". It never echoes script text or test names. Test names are dropped, because `Assertion` has no label (`crates/core/src/assert.rs:78-99`).

**Bounds.** Script text is capped at 64 KiB per request and charged to the import budget. Parsing is linear. No new dependency.

**Size:** +8 to +12 KB.

## Feature 5 — Private CA trust (user addition)

**Today.** `ClientCache::get` builds every client with `tls_certs_only(webpki_root_certs)` (`crates/core/src/client.rs:46-55`). reqwest 0.13.5 has two root modes:

- `tls_certs_only(...)` trusts only the given roots.
- `tls_certs_merge(...)` uses `rustls-platform-verifier` with those roots added as extra anchors (`~/.cargo/registry/src/*/reqwest-0.13.5/src/async_impl/client.rs:750-783, 1877-1906`).

`rustls-platform-verifier` 0.7.1 is already in `Cargo.lock`.

**Trust modes.** The engine holds one `TlsTrust { system: bool, extra: certificates }`:

| `system` | CA file | Verifier |
|---|---|---|
| off | none | bundled Mozilla roots only (0.4.0 behaviour) |
| off | set | bundled roots plus the file's certificates (`tls_certs_only`) |
| on | none | OS verifier, with the bundled roots as extra anchors (`tls_certs_merge`) |
| on | set | OS verifier, with the bundled roots and the file's certificates as extra anchors |

*Why the bundled roots stay in system mode:* on Linux the platform verifier fails when the OS store is empty (`rustls-platform-verifier-0.7.1/src/verification/others.rs:104-108`), which would break minimal containers. So system trust only ever adds trust. `verify_tls = false` on a request is unchanged. OAuth2 token requests share the `ClientCache` (`crates/core/src/auth/oauth2/manager.rs:467`), so they follow the same trust.

**Engine API.**

- `EngineConfig.tls: TlsTrust`.
- `Engine::set_tls_trust(TlsTrust)` drops the cached clients, so the next send uses the new trust. Requests in flight keep their client, and cookie jars are kept.
- `TlsTrust::load_pem_file(path)`:
  - only a regular file of at most 1 MiB;
  - at least one `CERTIFICATE` block, and every block must parse;
  - any private-key block is refused;
  - errors name the path and the reason, never the file's content;
  - no new crate.

**Where it is configured** (open questions 1-3; the recommendation is shown):

- **Per user only.** Neither a collection nor an environment can widen trust, because those files are shared through git. A CA file path is machine-specific, and a cloned repository must not be able to add a root. This is the same principle as the per-user send guard.
- **GUI:**
  - `settings.toml` gets a table:

    ```toml
    [tls]
    system_trust = true
    ca_bundle = "/abs/path.pem"
    ```

  - Three palette commands: "Toggle system certificate trust", "Choose CA certificate file…" and "Clear CA certificate file".
  - A file that fails to load leaves trust without it and shows a notice. This fails closed.
  - A TLS failure for an unknown issuer shows a one-line hint that names the commands.
- **`wisp-cli run`:** `--ca-bundle <file>` and `--no-system-trust`. It never reads `settings.toml`. An unreadable bundle exits 3, with nothing sent.
- **Default:** system trust on (open question 2), which fixes the reported homelab case with no configuration.

**Tests.**

- Fixture:
  - rcgen generates a private CA and a leaf certificate;
  - the leaf has SAN `127.0.0.1` and `localhost` and the serverAuth EKU;
  - the leaf is valid from now−1 h to now+30 d (macOS rejects TLS leafs valid for over 825 days);
  - `serve_tls` is extended (`crates/core/tests/tls.rs:42-80`).
- Cases:
  - bundled only fails with `Tls`;
  - with the file, bundled-only mode succeeds;
  - with the file, system mode succeeds;
  - system mode without the file fails;
  - `set_tls_trust` turns a failure into a success on the same engine;
  - the loader refuses a missing file, a directory, an oversized file, a key block, garbage, and a file with no certificate.
- These run on all three CI OSes (`.github/workflows/ci.yml:19`).
- The OS-store path with a real private root is a macOS hand test: the user's Caddy root in the System keychain.

**Size.** GUESS +5 to +60 KB. Whether LTO already strips the platform-verifier branch in 0.4.0 is not verified. Task 184 measures it on its branch.

## Per-user and security invariants

- Trust can only be widened by per-user settings or CLI flags, never by a collection, environment or request file. A CA file that fails to load never leaves trust wider than before.
- No secret value appears in a compare result's patterns, a warning, a notice, a log line or a history entry. Compare values are shown on screen only.
- An import warning never echoes script text, test names or a raw method.
- Tests never touch the real OS trust store or keychain. OS-store behaviour with a private root is hand-tested only.

## Risks

1. **OS verifier differences.** macOS and Windows may check revocation online, which can add latency or fail offline. Apple also enforces its own certificate rules (for example the 825-day limit). A public site that verified under 0.4.0 could fail under system trust. Mitigation: the off switch restores 0.4.0 behaviour, the docs say so, and the hand test covers a public site and the homelab one.
2. **Size of the platform verifier.** It is unknown (GUESS). Task 184 measures it on its branch before wave 2 builds on it.
3. **GraphQL `Body` sweep.** Every match on `Body` must handle the new variant; the compiler finds the exhaustive ones (for example `import/mod.rs:363`, `history.rs:422`, `history.rs:585`, `service/src/plan.rs:239`). Mitigation: one task owns the sweep, and the editor follows it.
4. **Forward compatibility.** 0.4.0 cannot read `graphql` bodies, or history entries whose request uses them. The release notes say so.
5. **`collection.toml` writes from the GUI.** The compare Ignore action writes a git-tracked file. The confirm step names the file, and the in-place write keeps comments.
6. **Test runner.** `cargo test` writes no JUnit XML and no reporter is installed, so checks follow the project's convention: a `command` check that greps the `test result: ok. N passed` line, with the new tests named by a prefix.

## Decisions (open questions answered 2026-11-19)

The user accepted all eight recommendations on 2026-11-19 ("Accept, fan out"). Each recommendation below is now a decision.

1. **Where is CA trust configured?** Decided: **per user only** (`settings.toml [tls]` for the GUI, flags for `wisp-cli run`), not in a collection or environment. Trust is a property of the machine; a CA path does not travel; and a shared repository must not be able to add a root.
2. **Is system trust on by default?** Decided: **on**. The OS store is added to the bundled roots, which fixes the homelab Caddy case with no configuration, and an off switch restores 0.4.0 behaviour. 3. **Does `wisp-cli run` read the GUI's `settings.toml [tls]`?** Decided: **no**. It uses flags only (`--ca-bundle`, `--no-system-trust`) with the same default as question 2. CI stays explicit, and the CLI keeps reading no per-user settings.
4. **Where does the compare ignore list live?** Decided: **`collection.toml [compare] ignore`**: one list per collection, shared and reviewable in git, with no `Request` frozen-type change. The alternatives are per request (a `Request` sweep plus a new dirty section) or per user (not shared).
