## Goal
The app opens one `SecretStore`, picked by platform and portable mode. It loads every environment through task 111's fail-closed loader, off the UI thread, and shows its status. It offers an Environment secrets panel to move an environment between file and keychain and to set or delete a keychain value. OAuth2 refresh tokens are persisted only for keychain-backed environments: this is the wave-2 seam.

## Decisions
- 2026-11-12, user decision, from code review of PR #55 at 45a5065: `KeychainRefreshStore::forget` touches the OS keychain only when the active environment is keychain-backed (status `Store{Keychain}`). For any other status, or a key with no collection/environment, `forget` returns `Ok(())` without any store call. For a keychain-backed environment a delete failure still fails the Authorize (fail closed). Reason: tokens are only ever stored for keychain-backed environments; before this, every auth-code Authorize called a keychain delete, so an unusable keychain (portable, no Secret Service, timeout) broke Authorize in file-mode environments too. Consequence: moving an environment from keychain to file (`migrate_to_file` flow) must also delete that environment's stored refresh tokens, so none survive the move; a delete failure there is reported to the user as a notice and does not undo the move. (AC18)
  - Amended 2026-11-12 (round 2), user decision: (a) Forget scope: forget is skipped (`Ok`, no store call) only for environments configured as file-mode, and for keys with no collection/environment. A keychain-mode environment always attempts the delete, whatever its load status (`Store{Keychain}`, `Failed`, `FellBackToFile`, ...); a delete failure fails the Authorize (fail closed). Reason: skipping forget for a keychain-mode env that loaded `Failed` broke core's "re-authorize replaces old tokens" invariant (crates/core/src/auth/oauth2/manager.rs:301, task 103): an earlier user's refresh token could be used again once the binding was fixed. (b) Stale tokens: `KeychainRefreshStore` keeps an app-maintained index entry per environment in the same `SecretStore` (one extra account, e.g. `<collection id>/<env>/oauth2-index`, listing that environment's refresh-token account names), updated on every save (add) and successful forget (remove). Move to file deletes every listed account and then the index, so tokens from earlier runs are removed too. No SecretStore/storage API change. Index contents are account names only, never secret values; it is subject to the same size limits (`MAX_SECRET_BYTES`): if adding an account would overflow it, the save fails closed with a clear error. The deletes run off the UI thread (AC2). (AC18)
- 2026-11-12, user decision, size gate: the Windows release binary at 05c0998 is 15,605,248 B, 105,248 B over the 15,500,000 B gate. A spike (CI runs 43302382570, 43307294831) showed keyring itself costs ~26 KB; most growth is wisp-storage vault/vault_binding code from 111/114 that 115 made reachable (~90 KiB), 115's app code, and generic instantiations. Dropping keychain support still leaves it over (15,534,080 B). Remedy: add `[profile.release.package.wisp-storage]` with `opt-level = "z"` to the root `Cargo.toml` (measured 15,171,072 B, 328,928 B under). The request engine (wisp-core) and UI (wisp-app) keep opt-level 3. This is a profile change, not the spec's "drop or replace the dependency" remedy; the scribe records that in the spec at /record. (AC10)
