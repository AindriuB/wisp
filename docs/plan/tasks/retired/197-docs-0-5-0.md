## Review round 1 — findings

- [P2] docs/architecture.md:268-279 (new "Collection binding and its trust assumption" paragraph). The binding rule it states is wrong, and it contradicts the residual it then describes.
  - The doc says "the common git dir must lie outside every collection root". The code (`verified_siblings_in`, crates/storage/src/vault_binding.rs ~956-985) does the opposite: it accepts a common dir that is exactly a bound root's own `.git`, and refuses only a common dir nested inside a root (`want.starts_with(&root) && want != root.join(".git")`). Only a bound main checkout with a real `.git` directory can anchor (`anchor_common_dir`). This is the AC5 narrowing that task 185 made (HISTORY.md:36-37).
  - The doc also says the nesting rule applies "when the worktree sits under another bound folder". The rule checks where the repository's common dir is, not where the worktree is.
  route: implementer — AC9 and the `accuracy` check need the binding text to match the merged code. No spec change is needed.
  input: Bind `~/repo` as a main checkout, then `git worktree add ~/wt`. Verification succeeds, but the doc's rule says `~/repo/.git` is inside a collection root and must be refused. Second case: bound collections `~/work` and `~/work/repo`, with a worktree at `~/elsewhere/wt`. Verification is refused (nesting), but the doc says nesting applies only to a worktree under a bound folder.
